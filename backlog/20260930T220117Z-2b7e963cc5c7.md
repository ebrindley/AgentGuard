# Define @project, split the installer, then add Pi and OMP

## Description

Bring Pi and Oh My Pi (OMP) under Agent Guard with at least pi-sandbox-guard's current protections, so Pi users can move to Agent Guard. Four parts, each its own pull request (docs/DESIGN.md section 12, step 10):

- **10a.** `@project` for OpenCode.
- **10b.** The installer split into modules with an action registry, before any Pi code.
- **10c.** The engine capabilities Pi needs, switched off for OpenCode, each with acceptance cases from pi-sandbox-guard's tests. Plus an unshipped Pi slice that runs the adapter's load cycle and the migration early.
- **10d.** The Pi profile, hooks, analyzer checker and migration.

After Pi works, write the "adding a harness" guide (docs/DESIGN.md section 14) from what Pi needed.

## Scope / Surfaces Affected

- 10a: list parser and launcher, for `@project` resolution (R7) and its refusal rules (docs/DESIGN.md section 4); `start_folder` in the OpenCode profile, for `opencode [project]` and the app launcher; `@project` in the snapshot.
- 10b: `profiles/opencode/install.sh` and `uninstall.sh`, split into `installer/lib.zsh`, `installer/actions.zsh`, `installer/harness/opencode.zsh` and `installer/migrate/opencode-guard.zsh`; `plan.json`, the stamp's `harnesses` and `migration.json` (docs/DESIGN.md section 6, Planned: installer structure).
- 10c: engine and plugin core: runtimes and executable precedence with `state/bindings.toml`; state roots, their root levels and `state/roots.json`; the protection union over installed harnesses; credential modes; git hooks; SBPL parameters; `rlimits`, pinned `path` and `refuse_env`; nested policies; `on_link`; the event log (docs/DESIGN.md sections 3 and 7). The Pi slice stays in test-only code.
- 10d: `engine/profiles/pi.toml` with runtimes `pi` and `omp`, the Pi Rust hooks and the shims `bin/pi` and `bin/omp`; `plugin/pi.mjs`, `plugin/pi-entry.ts` and `plugin/checkers/pi-analyzer/`; `installer/harness/pi.zsh` and `installer/migrate/pi-sandbox-guard.zsh`; `agent-guard bind`, `agent-guard wrapper add|remove|list` and `doctor --json`; the Pi suites carried over (docs/DESIGN.md section 8) and the conformance suite for the Pi profile; the Pi release notes; docs/DESIGN.md sections 11 and 14.
- Out of scope: replacing Pi's analyzer, adding cc-safety-net to Pi's chain or the analyzer to OpenCode's (docs/DESIGN.md section 5, Checker chain); switching any 10c capability on for OpenCode, each a later release of its own; `~/.config/pi-sandbox-guard/`, the legacy bundle's lifetime and archiving pi-sandbox-guard (step 11); other harnesses.

## Acceptance Criteria

**10a: `@project` for OpenCode**

- When `opencode` gets a positional project argument, `@project` is that folder, not the working directory.
- The app launcher's meaning of `@project` is defined after its effective working directory is measured, which is unverified today.
- When `@project` resolves to a refused folder (docs/DESIGN.md section 4), the launch is refused, not widened. The launch log shows what `@project` resolved to.
- When `@project` is not the launch folder, the protected names directly inside it get the same symlink resolution as those in the launch folder (docs/DESIGN.md section 3, Symlinks).
- With `@project` as the only ALLOW entry, two concurrent launches in different projects each write only their own project.
- New lists get `@project` commented out.

**10b: installer split**

- The split lands before any Pi code. The OpenCode install, update, uninstall, migration and recovery checks pass with no check changed or removed.
- Every switch action is an entry in an ordered action registry, with a phase label and paired do and undo handlers. `ag_switch_begun` and rollback derive from the registry, not a fixed name pattern, so an interrupted action of any harness is rolled back instead of discarded.
- The transaction's frozen recovery bundle holds every module the registered undo handlers need. Recovery succeeds with the new release folder and the stage deleted.
- `plan.json` names the harnesses being installed (the candidate inventory). Staged checks, the switch and the gate use it. The stamp's `harnesses` is written after the gate as the receipt. `doctor`, `update` and `uninstall` iterate over it, and a stamp without it reads as `["opencode"]`.
- `migration.json` is a list of `{from, switched_at, retired}`. An existing single object reads as a one-entry list, and retirement and forwarder removal keep working from it. One run migrates one source.
- Recovery passes after every registered action and after cleanup.

**10c: engine capabilities, OpenCode switched off**

- OpenCode switches none of these on. Its golden bytes, its snapshot contents and the step 2 checks are unchanged.
- Each capability runs under a test-only profile and has acceptance cases taken from pi-sandbox-guard's `test/shim.mjs` and `scripts/test-sandbox-profile.sh` at 7ad441f. Each case names its source check. A source case not carried over has a written reason (docs/DESIGN.md section 8). The capabilities:
  - **Executables** (docs/DESIGN.md section 3, Executables and launch links): `[runtime.<name>]` with `cli_names`, `cli_search`, `override_env` and `trusted_prefixes`. The order is the override variable under `trusted_prefixes`, then `state/bindings.toml`, then `cli_names` on `PATH` and `cli_search`. Every candidate is an executable regular file, is not a guard shim (pi-sandbox-guard's included, by location and content marker) and is outside the writable set. Harness and checker interpreters are separate records. A Homebrew Node is recorded as its formula's `opt` link. A stale binding fails closed with the recorded path and the `agent-guard bind` command that fixes it.
  - **State roots and the protection union** (section 3, Every installed harness): `state_hook`, `state_grants` and `state_config`; the three root levels (lexical families, the launch's own canonical roots with their ancestors pinned, recorded roots in `state/roots.json`). A linked root is protected, not refused. The union covers every harness in the candidate inventory during a transaction and in the stamp's `harnesses` after it. The launched profile's own protections are always included.
  - **Credentials** (section 3, Credentials): `credentials = "mandatory"` and `"list"`, including `~/.npmrc`'s `NPM_CONFIG_USERCONFIG=/dev/null`.
  - **Git hooks** (section 3, Git hooks): `hooks = "protect"`; R8 resolution with the probe environment and its refusals. The exceptions cannot reopen a list DENY or READ ONLY entry or the union. Collision cases cover a DENY and a READ ONLY over a project's `.git`, and a READ ONLY over an OMP worktree.
  - **Parameters** (section 3, SBPL parameters): named parameters for the R6 and R8 outputs. An unused runtime gets no parameter and renders no rule.
  - **`rlimits`, pinned `path` and `refuse_env`** (section 7, Launch pipeline, R4).
  - **Nested policies** (section 7, Nested launch): `nested = "same-boundary"` with the launch canary, its behavioral probes and boundary comparison, decided after R9, while `inherit` is decided after R5; a canary created in advance (EEXIST) refuses; refusal across profiles or runtimes (D3). An inherited launch writes no snapshot and uses the enclosing launch's release and executable.
  - **`on_link = "refuse"`** (C1), in the launch folder and in `@project`.
  - **Event log** (section 3, Event log): `~/Library/Logs/Agent Guard/`, writable and not readable inside the sandbox, rotated at launch outside the sandbox without following links.
- The snapshot gains the fields these need: runtime, state roots, active hooks folder, runtime grants, and the executable and interpreters used (section 7, Per-launch snapshot).
- TMPDIR validation is retired with its reason. One case shows that `TMPDIR=/` and `TMPDIR=$HOME` widen nothing.
- **Unshipped Pi slice**, in a disposable home, from test-only code the release archive does not contain:
  - a real Pi 0.99.2 loads the Pi adapter through `-e` and through the discovery link, and a copy whose release differs from `AGENT_GUARD_RELEASE` stands aside when Pi's arguments carry the launch release's injected copy, and otherwise hands over to the launch release, refusing when that release is missing;
  - after `/reload` and after a session replacement the handlers are registered again, and a refused call is still refused;
  - a dry migration against a fixture pi-sandbox-guard install detects every part, prints its plan and changes no file.

**10d: Pi and OMP**

- `pi.toml` is the Pi profile of docs/DESIGN.md section 3, with runtimes `pi` and `omp` selected by the shim's entry name. Pi's credential denies hold with no list entry (D2). The base template's exec and Launch Services denies apply to Pi (D7). A set `PI_PACKAGE_DIR` refuses the launch.
- The `args_hook` classifies agent sessions, extension-loading commands, administrative commands and refused commands, with option precedence. `-e <launch release>/plugin/pi-entry.ts` is injected for every command that loads extensions and not for the administrative ones (docs/DESIGN.md section 5, Plugin injection by command). OMP keeps pi-sandbox-guard's tables, and refuses `cleanse`, `commit` and `join`.
- pi-sandbox-guard #8 behavior holds, widened as docs/DESIGN.md section 3 plans: `.pi` and `.omp` and the other-harness extension, hook and tool folders it lists are denied for write and creation, including rename and symlink planting, anywhere on disk except inside a Pi or OMP root. A symlinked `.pi` or `.omp`, or one holding a link to a writable place outside it, refuses the launch.
- #9 behavior holds: Pi user package and configuration state (`settings.json`, `auth.json`, `trust.json`, `SYSTEM.md`, `APPEND_SYSTEM.md`, `models.json`, `*prompt*.md`, `extensions/`, `npm/`, `git/`, `skills/`) and OMP's configuration are write-denied at every root level, including under a `PI_CODING_AGENT_DIR` relocation and a family root linked elsewhere. Sessions and themes stay writable.
- #10 behavior holds: Homebrew Node bindings use the formula's stable `opt` link, and each launch checks each Node binding's current target against the writable set. A stale binding fails closed with the recorded path and the `agent-guard bind` command.
- `executables.conf` and `.guard-node` are imported into `state/bindings.toml` through the same validation as a launch, and used. `PI_EXECUTABLE` and `OMP_EXECUTABLE` still come first under the trusted prefixes. A native Pi or OMP target with no harness interpreter launches, and the analyzer runs on the checker interpreter.
- Active git hooks stay write-denied throughout the migration: the default `.git/hooks` and a `core.hooksPath` target, plus linked worktree, submodule and OMP-managed worktree hooks.
- Relocated Pi state and the active OMP profile (`omp --profile <name>`) get the same protection as the defaults. OMP keeps its positive state allowlist, as `state_grants`, and its documented `agent.db` limitation.
- The Pi adapter checks `read`, `grep`, `find`, `ls`, `edit` and `write` against the projection, including the runtime grants, so no file-tool check refuses a write Seatbelt permits on purpose. `bash` and `powershell` go to the checker chain. The adapter registers on every load. A copy whose release differs from `AGENT_GUARD_RELEASE` stands aside only when Pi's arguments carry the launch release's `-e` copy, and otherwise hands over to that release (docs/DESIGN.md section 5, Plugin core and adapters). Only the registering copy registers the status tool. A Pi started directly inside an OpenCode session finds OpenCode's snapshot and refuses tools as unguarded. Asks go through `ctx.ui.confirm` when `ctx.hasUI` and are refused otherwise; in RPC mode the client answers (D4).
- Pi keeps its analyzer as the `pi-analyzer` checker for `bash` input (D5). It moves unchanged except for the log path (`~/Library/Logs/Agent Guard/`, umask 077, mode 0600, full command text) and the interpreter source. The 383 corpus cases give the same verdicts through the core, and the pinned gap stays pinned.
- An unguarded Pi refuses every tool outside the Pi safe set after the behavioral probe, where pi-sandbox-guard only warned when `PI_SANDBOX_PROFILE_DIGEST` was missing. The Pi release notes state this behavior change (docs/DESIGN.md section 11). The safe set is listed in docs/DESIGN.md section 5.
- Every launch protects both installed profiles' files, so an ALLOW entry cannot expose the other harness's plugin, configuration or bindings.
- The Pi migration follows docs/DESIGN.md section 11, The Pi migration: detect, refuse while Pi or OMP runs, stage and run `check staged` for the Pi profile, confirm policy, import, switch in the journaled order, gate on `doctor` for both profiles, and, after the stamp, retire the original shims, `pi-sandbox.sb`, `pi-sandbox-preamble.zsh`, the launcher stamp, the extension, the launcher backups, `~/.pi/agent/extension-backups/` and `~/.pi/agent/security-events.log` into `state/legacy/pi-sandbox-guard/`, deleting nothing. `~/.config/pi-sandbox-guard/` is left in place and unchanged.
- Policy confirmation (D1): the migration shows what the shared list means for Pi and asks even when the list needs no edit. With `ALLOW ~/Projects`, Pi gains write access to every project there. It proposes `@project` when no ALLOW entry covers Pi's projects. No answer, or no terminal, changes nothing.
- A gate failure or an interruption rolls back from the journal and the backup, leaving pi-sandbox-guard's files byte-identical to before. Recovery passes after every registered Pi action and after cleanup.
- On a Mac with both old guards, the first run migrates OpenCode Guard and the next migrates pi-sandbox-guard.
- Uninstall after a Pi migration removes the `~/.local/bin` links, the discovery link and the bindings with the engine folder. It does not reinstate pi-sandbox-guard. It first copies the legacy bundle to `~/Agent Guard/pi-sandbox-guard-legacy/`, keeping the engine and exiting 1 if the copy fails, then prints the steps that would, naming that copy (D6).
- Custom Pi wrapper scripts keep their paths and arguments. `scripts/check-launchers.mjs --sources` runs once against them before the switch; `--deployed` is not used, because it expects zsh shims. Their names, historical names and hashes are imported into `state/wrappers.json`. `agent-guard wrapper add|remove|list` applies the validation of `deploy:launchers --extra-launchers`, including the rejection of reserved and duplicate names. `remove` deletes a wrapper whose content matches its recorded hash and keeps its name as historical.
- `agent-guard bind` replaces `scripts/bind-executable.sh` with `--show`, `--check` (non-zero when stale), `--detect` and explicit `--pi`, `--omp`, `--node` (harness interpreter) and `--checker-node` (checker interpreter) paths. It refuses to run inside the guard, confirms through the terminal and writes atomically.
- `agent-guard doctor --json` reports, per profile: release file hashes against the release manifest, binding and checker-interpreter staleness, wrapper hashes and retired wrappers still executable, entry-point resolution in a login shell, and relocation variables. `doctor` runs the checker preflight for each profile's chain.
- OMP is re-observed before its tables ship: extension discovery folders, real-path deduplication, `-e` handling, tool names, the command list, `cleanse`, `commit`, `join`, and the runtime paths behind the allowlist. Each difference from pi-sandbox-guard's tables is recorded in docs/DESIGN.md section 11.
- The Pi suites carried over (docs/DESIGN.md section 8) pass. The plugin case table runs through a driver per adapter, with the Pi lifecycle cases: `/reload`, session replacement, discovered plus injected copies of one release and of two releases, and an update between discovery and injection. `scripts/test-ops.sh`'s cases run in CI as installer and migration tests.
- The Pi release notes include the compatibility matrix of docs/DESIGN.md section 11 for Pi and OMP and for OpenCode.
- Pi and OMP run under Agent Guard on the owner's Mac, and the conformance suite passes for the OpenCode and Pi profiles. The "adding a harness" guide lists the five parts (profile data, hooks, plugin adapter, checkers, conformance pass) and what Pi needed beyond the OpenCode profile.

## How to Verify

- 10a: with `@project` as the only ALLOW entry, run `opencode <folder>` from another working directory. The log shows `<folder>` as `@project`, a write in `<folder>` succeeds and a write in the working directory is denied.
- 10b: `zsh test/test.sh`, `zsh test/install.sh`, `zsh test/migrate.sh` and `zsh test/bootstrap.sh` pass, and `git diff` shows no check changed. Kill a run after each registered action and after cleanup, then rerun: each outcome matches docs/DESIGN.md section 10, Recovery testing. Install over the stamp and `migration.json` of the release before the split: `doctor`, `update` and forwarder removal work.
- 10c: the golden test passes unchanged. Each capability's cases pass under the real `sandbox-exec`, and each names its source check. `tar -tzf` of the release archive lists none of the slice's files.
- 10d: run the conformance suite for both profiles outside any agent sandbox. Each #8 and #9 path and name is denied for write, creation and symlink replacement at each root level. Active hooks are denied at each surface, and the hooks collision cases hold.
- The carried-over Pi suites pass against Agent Guard.
- `node scripts/check-launchers.mjs --sources <wrapper>...` from pi-sandbox-guard passes for the custom wrappers. Each wrapper then launches Pi guarded with its arguments.
- Start Pi without the guard: tools are refused with the relaunch message.
- In a fixture, move a Node `opt` link to a new Cellar version: launches keep working without a rebind. Point a binding at a missing path: the launch fails closed.
- Against a fixture pi-sandbox-guard install, fail the gate: pi-sandbox-guard's files are byte-identical to before. Complete a migration, then uninstall: every file the printed steps name exists under `~/Agent Guard/`.
- Before the switch on the owner's Mac, save `npm run status -- --json` from pi-sandbox-guard. After it, `agent-guard doctor --json` reports the same bindings, wrappers and relocation variables.
- On the owner's Mac, follow pi-sandbox-guard's `test/e2e-demo.mjs` as the manual Pi check.

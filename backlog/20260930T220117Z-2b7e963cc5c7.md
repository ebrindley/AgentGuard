# Define @project for OpenCode, then add the Pi and OMP profile

## Description

Define `@project` for OpenCode, then add the Pi and Oh My Pi (OMP) profile with pi-sandbox-guard's current protections, so Pi users can move to Agent Guard. After Pi works, write the "adding a harness" guide from what Pi needed.

## Scope / Surfaces Affected

- List parser and launcher: `@project` resolution and its refusal rules (docs/DESIGN.md section 4).
- OpenCode profile: what `@project` means for `opencode [project]` and for the app launcher.
- New Pi profile with its Seatbelt fragment and state hook (docs/DESIGN.md sections 3 and 11).
- Pi plugin adapter around Pi's existing analyzer (docs/DESIGN.md section 5).
- Installer: detect a pi-sandbox-guard install, import `~/.config/pi-sandbox-guard/executables.conf` into the engine folder, replace the `~/.local/bin/{pi,omp}` shims with backups, propose the list change once (docs/DESIGN.md sections 4 and 11) and remove the old extension.
- Pi test suites carried over (docs/DESIGN.md section 8) and the conformance suite for the Pi profile.
- docs/DESIGN.md section 14: the "adding a harness" guide.
- Out of scope: replacing Pi's analyzer with cc-safety-net (a separate decision after the corpus run), archiving pi-sandbox-guard (step 11) and other harnesses.

## Acceptance Criteria

**`@project` for OpenCode**

- When `opencode` gets a positional project argument, `@project` is that folder, not the working directory.
- The app launcher's meaning of `@project` is defined after its effective working directory is measured, which is unverified today.
- When `@project` resolves to a refused folder (docs/DESIGN.md section 4), the launch is refused, not widened. The launch log shows what `@project` resolved to.
- With `@project` as the only ALLOW entry, two concurrent launches in different projects each write only their own project.

**Pi and OMP**

- pi-sandbox-guard #8 behavior holds, widened as docs/DESIGN.md section 3 plans: `.pi` and `.omp` and the other-harness extension, hook and tool folders it lists are denied for write and creation, including rename and symlink planting, anywhere on disk except inside Pi's and OMP's own state folders.
- #9 behavior holds: Pi user package and configuration state (`settings.json`, `auth.json`, `trust.json`, `SYSTEM.md`, `APPEND_SYSTEM.md`, `models.json`, `*prompt*.md`, `extensions/`, `npm/`, `git/`, `skills/`) is write-denied, including under a `PI_CODING_AGENT_DIR` relocation. Sessions and themes stay writable.
- #10 behavior holds: Homebrew Node bindings use the formula's stable `opt` link, and each launch checks each Node binding's current target against the writable roots. A stale binding fails closed with the recorded path and the command to fix it.
- Bindings from `executables.conf` are imported and used.
- Active git hooks stay write-denied throughout the migration: the default `.git/hooks` and a `core.hooksPath` target, plus linked worktree, submodule and OMP-managed worktree hooks.
- Relocated Pi state and the active OMP profile (`omp --profile <name>`) get the same protection as the defaults. OMP keeps its positive state allowlist and its documented `agent.db` limitation.
- Custom Pi wrapper scripts keep their paths and arguments. `scripts/check-launchers.mjs --sources` is run once against them; `--deployed` is not used, because it expects zsh shims.
- Pi keeps its analyzer as the Pi plugin. The Pi release notes state the behavior change: an unguarded Pi now refuses tools after a behavioral probe, where pi-sandbox-guard only warned when `PI_SANDBOX_PROFILE_DIGEST` was missing (docs/DESIGN.md section 11).
- Every launch protects both installed profiles' files, so an ALLOW entry cannot expose the other harness's plugin or bindings.
- Pi runs under Agent Guard on the owner's Mac, and the conformance suite passes for the OpenCode and Pi profiles. The "adding a harness" guide lists the four parts and what Pi needed beyond the OpenCode profile.

## How to Verify

- Conformance suite for both profiles, outside any agent sandbox. Each #8 and #9 path and name is denied for write, creation and symlink replacement; active hooks are denied at each surface.
- The carried-over Pi suites pass against Agent Guard.
- With `@project` as the only ALLOW entry, run `opencode <folder>` from another working directory: the log shows `<folder>` as `@project`, a write in `<folder>` succeeds and a write in the working directory is denied.
- `node scripts/check-launchers.mjs --sources <wrapper>...` from pi-sandbox-guard passes for the custom wrappers. Each wrapper then launches Pi guarded with its arguments.
- Start Pi without the guard: tools are refused with the relaunch message.
- In a fixture, move a Node `opt` link to a new Cellar version: launches keep working without a rebind. Point a binding at a missing path: the launch fails closed.

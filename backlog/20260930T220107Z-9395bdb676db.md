# Port OpenCode Guard's v1.0.4 fixes into the zsh engine

## Description

Port the five OpenCode Guard changes made after v1.0.3 into `engine/` and `profiles/opencode/`, with their test additions, so a Mac running a build later than v1.0.3 loses no fix at the switch. OpenCode Guard's v1.0.4 tag (`1ac39a2`) is v1.0.3 plus exactly these commits and rebuilt DMG and zip files. This is the first change of step 3 and lands on its own, before the renames, so it keeps OpenCode Guard's identifiers (`opencode_guard_status`, `OPENCODE_SANDBOXED`).

## Scope / Surfaces Affected

Read each commit with `git show <commit>` in the OpenCodeGuard repository. Paths map as follows: `plugin/opencode-guard.js` to `profiles/opencode/plugin.js`, `vendor/` to `engine/vendor/`, `templates/` to `profiles/opencode/templates/`, `install.sh` to `profiles/opencode/install.sh`, the check-mode plugin probe in `engine/launch` to `opencode_check` in `profiles/opencode/hooks.zsh`, and `test/` to `test/`.

| Commit | Change | Here |
|---|---|---|
| `2e93cf3` | When guarded, the plugin deletes `CC_SAFETY_NET_HOME`, `CC_SAFETY_NET_WORKTREE` and `SAFETY_NET_WORKTREE` and sets `CC_SAFETY_NET_PARANOID_RM=1` before loading cc-safety-net. The launcher does the same in every mode, including nested launches and `check`. | `plugin.js`. In `harness.zsh`, add the two worktree variables to `env_unset`. `engine/launch` applies these unsets and `CC_SAFETY_NET_PARANOID_RM=1` before the nested-launch check. The nesting marker is still exported only just before `sandbox-exec`, because exporting it earlier would trip the nested-launch check. |
| `13a5aa1` | `exec`, `nice`, `nohup`, `setsid`, `stdbuf`, `time` and `timeout` join `env` in `transparent_wrappers`. The install merge takes the wrapper list from the bundled `rule.json`, and its invalid-JSON warning names all eight. | `templates/cc-safety-net/rules/rule.json`, `install.sh` |
| `14e0e85` | Check-mode `serve` output goes to `$engine/state/.serve.<pid>`, not the per-user temp folder. That folder is writable from inside the sandbox, so a planted symlink could redirect the launcher's unsandboxed write, and a replaced file could point the check at another server. | `hooks.zsh` |
| `3fd2703` | The check's polling loop stops when `serve` exits, so a server that answers on the port after `serve` died cannot pass the plugin check. | `hooks.zsh` |
| `85dc43f` | Vendor cc-safety-net 2.4.14. Custom rules now apply to nested commands (upstream #139), so recursive `rm` is blocked inside `bash -c`, `sh -c`, `eval` and `env -S`. | `engine/vendor/cc-safety-net/`, replaced in full: three chunk files are removed and three added |

- Tests, in `test/plugin.mjs` guarded mode: recursive `rm` stays blocked when `CC_SAFETY_NET_HOME` points at a permissive config (with the permissive `rule.json` that `test/test.sh` writes under `Projects/net`), behind `timeout 5`, inside `bash -c` and inside `env -S`. The two check-mode commits added no tests.
- `README.md` states no cc-safety-net version. Its sentence "bundled cc-safety-net is unchanged" becomes false and says 2.4.14 instead.
- docs/DESIGN.md: the cc-safety-net version (sections 2 and 5), the `harness.zsh` listing and `env_unset` row (section 3), the plugin's environment handling (section 5), the wrapper entries uninstall leaves (section 6), what an OpenCode Guard install contains (section 10: v1.0.4 adds the extra wrappers) and the check counts (section 8).
- The generated SBPL does not change. Reading the five diffs: none touches `profile.sb`, the protected fragment, `writable` or the list and profile builder. `2e93cf3` changes only exported environment, and `14e0e85` and `3fd2703` change only the check branch, so none changes what `launch profile` prints. The golden test must pass unchanged against the unchanged v1.0.3 fixtures.
- Out of scope: the renames (the rest of step 3), OpenCode Guard's DMG and zip, and changes to the OpenCodeGuard repository.

## Acceptance Criteria

- `diff -r engine/vendor/cc-safety-net <OpenCodeGuard at 85dc43f>/vendor/cc-safety-net` prints nothing, and `package.json` gives version `2.4.14`.
- `profiles/opencode/templates/cc-safety-net/rules/rule.json` lists the eight wrappers. An install over an existing `rule.json` adds any wrapper that is missing and keeps its other entries.
- Guarded, the plugin removes the three variables and sets `CC_SAFETY_NET_PARANOID_RM=1` before cc-safety-net loads. Unguarded, it leaves the environment alone.
- `launch cli`, the nested-launch path and `launch check` run their child with the three variables unset and `CC_SAFETY_NET_PARANOID_RM=1`.
- `launch check` writes its `serve` output only to `state/.serve.<pid>`, never to the per-user temp folder, and removes it afterwards. When `serve` exits early, the check stops polling and prints `FAIL plugins not loaded in OpenCode`.
- `node test/golden.mjs` passes with `test/fixtures/opencode-guard-1.0.3/` unchanged.
- `zsh test/test.sh` reports 0 failures, and its check list is the base commit's plus the four guarded plugin checks above (76 in total over stage 1's 72).

## How to Verify

- For each commit, run `git show <commit>` in OpenCodeGuard next to `git diff` of this change and confirm each hunk has a counterpart at the mapped path. The only intended differences are those path mappings and the `env_unset`/`env_set` placement.
- Run `diff -r` for the vendor folder.
- Run `launch profile` for the two golden lists on the base commit and on the change, and compare the outputs byte for byte. They are identical.
- Outside any agent sandbox, run `node test/golden.mjs` and `zsh test/test.sh`.
- In the disposable home, run `launch check` and then list the per-user temp folder and `state/`. Neither holds a serve output file.

# Move OpenCode onto shared credentials and hooks, then compose sessions

## Description

After Pi's migration (step 10d), move OpenCode onto the capabilities step 10c built, one change per release, and compose each session from the harnesses present at launch, so that a harness started inside another harness's session runs under that session's sandbox instead of being refused (docs/DESIGN.md section 11, OpenCode's releases; section 3, Composition). Five releases, in this order:

1. **The executable release.** OpenCode's executable and launch links are checked against the writable set.
2. **The credentials release.** The credential set applies to OpenCode.
3. **The hooks release.** Git hook protection applies to OpenCode, including the app, whose project folder step 10a defines.
4. **The composition release.** Every launch, Pi's and OpenCode's, grants and protects every present harness, lists them as members in its snapshot and carries a launch canary. It ships only after the gate below.
5. **The nested-launch release.** OpenCode moves from `nested = "inherit"` to the shared nested rule, and the `nested` field is removed.

One rule holds throughout: no session can write configuration. Each release reaches both Macs through `update`, and its release notes state what stops or starts working inside sessions.

## Scope / Surfaces Affected

- Executable release: C2 for OpenCode (docs/DESIGN.md section 3, Executables and launch links; section 7, Launch pipeline): the selection procedure every profile uses (override, recorded binding, `PATH`, `cli_search`, skipping guard shims) and the writable-set check on the executable and every launch link. Only an `inherit` nested launch keeps today's PATH search, until the nested-launch release.
- Credentials release: the engine switch that leaves the credential set off for OpenCode is removed; OpenCode's plugin projection gets the credential classes (docs/DESIGN.md section 3, Credentials).
- Hooks release: the switch that leaves Git hooks off for OpenCode is removed; R8 in `gui` mode uses the project folder step 10a defines; the Agent Guard rulebook for cc-safety-net gains a rule that blocks `core.hooksPath` changes (docs/DESIGN.md section 3, Git hooks; section 5).
- Composition release, for every profile: presence, member grants and protections, the combined executable check, member records in the snapshot, snapshot acceptance by membership in the plugin core, a canary in every launch, every granted member's roots in `state/roots.json` (docs/DESIGN.md section 3, Composition; section 7, Launch pipeline, Per-launch snapshot and Nested launch).
- Nested-launch release: OpenCode's `nested` value and the field itself; OpenCode's nested launches use the snapshot's member record instead of searching PATH.
- docs/DESIGN.md sections 3, 7, 9, 11 and 15, `README.md`, the release notes, the golden test's recorded differences and the conformance suite, as each release lands.
- Out of scope: other harnesses; moving and read-denying the cc-safety-net audit log (a separate OpenCode opt-in, docs/DESIGN.md section 3, Event log); the SSH agent socket, persistent-instruction folders and Pi's OAuth refresh (captured items).

## Acceptance Criteria

**Every release**

- OpenCode's golden test compares against the v1.0.3 fixtures plus the recorded differences; each release's recorded difference holds only that release's rules.
- The conformance suite passes for the OpenCode and Pi profiles, and terminal launch, app launch and `doctor` pass on each Mac after `update`.

**1. The executable release**

- When OpenCode's executable, or a link on the way to it, resolves inside the writable set (for example under an `ALLOW /opt/homebrew` entry), that candidate is not used. When no candidate passes, the launch refuses and names the rejected path.
- With no binding, no override and no ALLOW entry over the executable's folders, the same executable is selected as before, and OpenCode's profile bytes do not change.
- A stale binding refuses with the `agent-guard bind` command that fixes it.

**2. The credentials release**

- OpenCode launches apply the credential set as Pi's do. Inside OpenCode sessions, Git over SSH, HTTPS pushes that use `gh` as the credential helper, GPG signing, Docker and Kubernetes logins, `gh` itself and all of npm's user config (registries, proxies, the CA file) stop working, and `.env` files cannot be read apart from `.env.example`, `.env.sample` and `.env.template`. Cloud CLIs keep working, and AWS token refreshes are saved.
- OpenCode's plugin projection refuses reads of tool credentials and allows reads of inference credentials and the template names, matching Seatbelt. cc-safety-net's secret-path checks still refuse file-tool reads of `~/.aws` and gcloud's configuration (docs/DESIGN.md section 5, Checker chain); OpenCode's own provider reads succeed.
- A `{file:...}` key file under `~/.secrets` named in OpenCode's config in `~/.config/opencode` loads. When a project config, `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, a relocated `XDG_CONFIG_HOME` or remote config names a denied file, OpenCode stops at startup with its config error (OpenCode 1.18.34 substitutes `{file:...}` in every config it loads).
- In an OpenCode session, Bedrock with SSO, `aws login` and `credential_process`, Vertex with and without `GOOGLE_CLOUD_PROJECT`, and Azure through `az` work, as the step 10c provider cases showed.
- The release notes state the changes above, that for Vertex models served through the OpenAI-compatible SDK, when the credential file names no `project_id`, setting `GOOGLE_CLOUD_PROJECT` stops OpenCode's Google library from running `gcloud` on each request, that Vercel AI Gateway needs `AI_GATEWAY_API_KEY` because a Vercel CLI login cannot be refreshed inside a session, that the `.env` template exemption relies on file names, and that a project config naming a denied `{file:...}` stops OpenCode at startup.

**3. The hooks release**

- Git hook protection applies to OpenCode in `cli` and `gui` mode; in `gui` mode R8 resolves the hooks folder from the project folder step 10a defines.
- OpenCode sessions get the Git selector unsets, and R8 runs with OpenCode's own `XDG_CONFIG_HOME`.
- A shell command that changes `core.hooksPath` is refused by the Agent Guard rulebook rule in cc-safety-net. It refuses rather than asks: OpenCode's `tool.execute.before` hook can only throw, and cc-safety-net has no ask verdict.
- The release notes state: hook managers (husky, lefthook, pre-commit) cannot install hooks inside a session; a versioned hooks folder set as `core.hooksPath` cannot be edited from a session; a hooks path that is the home folder, too broad or contains the project refuses the launch; only the launched project's hooks are protected; a `GIT_CONFIG_GLOBAL` or similar variable set by the user does not reach sessions.

**Gate before the composition release**

- Each item below is protected, checked at launch, or accepted in writing in docs/DESIGN.md section 9, Other code in writable folders. Protection comes first wherever the harness tolerates it, because a launch check helps only guarded starts and unguarded starts are where these escape:
  - `wellknown` entries in OpenCode's `auth.json`, which make OpenCode fetch remote config at startup and merge it as global config, including plugins and MCP commands;
  - OMP stored keys starting with `!`, which OMP runs through `/bin/sh -c` at key lookup;
  - OMP's code folders: `python-env` (its Python runtime), `natives` (its native add-on) and `puppeteer` (Chromium);
  - OMP's `models.db` model cache, whose cached endpoint overrides survive loading, so a rewrite can redirect keys (checked at step 10d);
  - Pi's compiled-extension cache (docs/DESIGN.md section 15, To verify).
- Each protection or launch check has a conformance case. The composition release is not tagged until every item has its recorded disposition.

**4. The composition release (every launch)**

- Presence: a runtime (Pi and OMP count separately) is present when it is installed in Agent Guard and its CLI resolves the normal way: override, then recorded binding, then PATH, then known locations, skipping guard shims. Presence is decided once, at the outer launch, and recorded. During an install, the transaction's candidate list counts as installed.
- Executable check: the combined writable set is built once from every member whose folders resolve. Each member's executable, interpreters and launch links are checked against it. A member that fails is dropped and removed from the snapshot's members, and the set is not rebuilt; when the failing member is the harness being launched, the launch refuses.
- Grants: each present member gets its `writable` folders and `state_grants`. The launched harness takes its folders from its own arguments, for example `omp --profile work`; the other members take theirs from the environment: OMP's base from `PI_CONFIG_DIR`, its profile from `OMP_PROFILE` or `PI_PROFILE`, otherwise the default, never every profile. A member whose folders do not resolve gets no grants and does not stop the launch. OpenCode's app folders are granted only for an app launch.
- OMP as a granted member: when its `.env` check finds a forbidden variable, OMP is dropped from the members and gets no grants; its lexical protections still apply.
- Protections: every installed harness is protected, present or not: its protected paths and names, its configuration at all three root levels and its denies inside granted folders. Every granted member's state roots are protected like the launched harness's own and recorded in `state/roots.json`. OMP worktree hook denies render whenever OMP's `wt/` folder is granted, including in another harness's session. A protection that has to be looked up (a `protected` entry's link target, a relocated package store, a recorded root) and cannot be refuses the launch.
- Snapshot: it lists the members and, for each, its executable and interpreters, its command checker and settings, its plugin arguments, its state roots and OMP profile, plus one projection covering every combined grant. Before this release a snapshot names one profile and runtime. A harness's plugin trusts a snapshot that lists it and uses its own record from it. Nested launches write no second snapshot, and plugin code stays at the outer launch's release. Every launch gets a canary.
- Pi inside OpenCode: a `pi` or `omp` launch inside an OpenCode session whose snapshot lists it runs under that session's sandbox when the nested rule holds (docs/DESIGN.md section 7, Nested launch), and otherwise refuses with the reason. A Pi started directly inside such a session checks its tools against Pi's member record instead of refusing them as unguarded.
- An OpenCode request inside a Pi session keeps OpenCode's `inherit` behavior, including its PATH search, until the nested-launch release.
- A harness installed during a session is not a member until the session restarts. An uninstalled harness keeps its grants until the session ends.
- docs/DESIGN.md and the release notes state the accepted cost: every session can write every present member's runtime data. That is OpenCode's `~/.local/share/opencode` (logins in `auth.json`, sessions), `~/.local/state/opencode`, `~/.bun/install/cache` and `~/.cc-safety-net/logs`; Pi's sessions and caches; OMP's `agent.db` (logins and runtime data), `browser-relay`, `ssh-control`, `secret-placeholder.key` and its code folders as the gate leaves them; in an OpenCode app session, the app's folders too. Any session can therefore delete or replace another harness's logins and poison its sessions and memory. Configuration stays locked everywhere.

**5. The nested-launch release**

- OpenCode uses the shared nested rule: an `opencode` launch inside a session whose snapshot lists OpenCode runs under that session's sandbox when the rule holds, with the member record's executable; OpenCode's nested launches no longer search PATH.
- OpenCode inside a Pi session runs from this release.
- OpenCode inside an OpenCode session in a different project is refused, naming the project. The release notes state this as the cost of requiring the same project.
- The `nested` field is gone from the profile schema, and the conformance check rejects it.

**Composition cases**, under the real `sandbox-exec` in a disposable home with both profiles installed, at the composition release, and the OpenCode-request cases again at the nested-launch release:

- A nested launch in the same project runs; a subfolder of the same repository counts as the same project.
- A nested launch with a different project, OMP profile or active hooks folder refuses and says which.
- A READ ONLY entry over a member's state folder makes that member's nested launch refuse, naming the entry.
- A member whose executable lies inside the combined writable set is dropped and its nested launch refuses; when it is the launched harness, the launch refuses.
- A symlinked protected name in a nested launch's folder whose target the outer sandbox does not lock refuses.
- A relocated OMP folder (`PI_CONFIG_DIR`) granted to an OpenCode session has its configuration write-denied and is recorded in `state/roots.json`.

## How to Verify

- Each release: the golden test with that release's recorded difference, the conformance suite for both profiles outside any agent sandbox, and the per-Mac checks after `update`.
- Executable release: in a disposable home, put a fake `opencode` inside an ALLOW folder first on `PATH`. The launch does not run it and names it when no other candidate passes.
- Credentials release: on the owner's Mac, rerun the step 10c provider cases through OpenCode's own launches. Inside an OpenCode session, `git push` over SSH fails and `ssh-add -l` finds no agent; reading `.env` fails and reading `.env.example` succeeds.
- Hooks release: run the hooks collision cases for the OpenCode profile in `cli` and `gui` mode. Ask OpenCode to run `git config core.hooksPath x`: cc-safety-net refuses it.
- Gate: docs/DESIGN.md section 9 lists every gate item with its disposition, and the conformance suite has a case for each protection or check.
- Composition and nested-launch releases: the composition cases above pass, and Pi started from an OpenCode session reports the guard active with Pi's member record.

## Dependencies

- Step 10d (Pi and OMP under Agent Guard, with the step 10c capabilities)
- Step 10a (the app's project folder), for the hooks release
- Within this item: the releases ship in order; the composition release also needs the gate, and the executable check it applies to every member is the executable release's.

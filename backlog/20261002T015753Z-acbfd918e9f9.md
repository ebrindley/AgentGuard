# Add credential and Git-hook protection to OpenCode

## Description

Pi and Grok sessions cannot read or write the named credential paths, and Pi sessions cannot write the project's active Git hooks. OpenCode sessions have neither: the OpenCode profile denies only what the Guard List names. Add both to the OpenCode profile on the zsh engine (docs/DESIGN.md section 12, step 10e; decision D12), one release each.

## Scope / Surfaces Affected

- OpenCode profile data and `engine/launch`: the credential set Grok uses (`profiles/grok/harness.zsh` `credential_paths`, `credentials.sb`, `env_unset`, `env_set`), and the active Git hooks resolved at launch as Pi's profile does.
- docs/DESIGN.md section 3, SECURITY.md and USAGE.md: what stops working inside OpenCode sessions.
- Golden fixtures: each change recorded as a difference.
- Out of scope: composition, nested-launch policies and the executable release of the original step 10e (D12).

## Acceptance Criteria

- Credentials release: inside an OpenCode session, the named credential paths and `.env` files (not `.env.example`, `.env.sample` or `.env.template`) can be neither read nor written, `SSH_AUTH_SOCK` and `GPG_AGENT_INFO` are unset, and npm's user configuration is disabled. `gh` and `git` over HTTPS keep working through the keychain.
- Hooks release: the active Git hooks, as resolved at launch, are write-denied, and creating or replacing them is refused.
- Each release's notes state what stops working inside OpenCode sessions.
- `node test/golden.mjs` passes with each release's recorded difference only.

## How to Verify

- Disposable-home tests under the real `sandbox-exec`: read and write of each credential path, `.env` and its allowed variants, and each hook path.
- Inside an OpenCode session: `git push` over HTTPS works; reading `.env` fails and reading `.env.example` succeeds.

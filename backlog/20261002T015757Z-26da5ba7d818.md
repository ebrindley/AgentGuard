# Decide how Pi OAuth logins refresh inside the guard

## Description

Pi saves the API keys and OAuth tokens of `/login` in `<agent-dir>/auth.json` (Pi 0.99.2 documentation, `docs/providers.md`). An OAuth refresh writes that file through Pi's credential store, and a failed write throws "Credential store modify failed". The guard write-denies `auth.json` as Pi configuration (`state_config`; docs/DESIGN.md section 3, Planned Pi profile), and it has to stay locked because it runs programs: a provider `key` starting with `!` is run as a command. So a Pi OAuth login stops at its first refresh inside a session, and Pi reports a credential-store error. pi-sandbox-guard 7ad441f behaves the same: `sandbox/pi-sandbox.sb` write-denies `auth.json`. Step 10d ships this as a known limitation in the Pi release notes.

Options:

- (a) A Pi upstream change to where refreshed logins are written: tokens in a file separate from `auth.json` that holds no keys or commands, which the Pi profile could grant.
- (b) A separate writable token store: refreshed tokens go to a place sessions may write, while `auth.json` stays locked. Whether Pi 0.99.2 lets an extension supply or store credentials is unverified.
- (c) Accept: OAuth logins are made and refreshed outside the guard, and the release notes say how.

Inference, to check with (c): `/login` inside a session writes the same file, so a new login cannot be saved inside the guard either.

## Scope / Surfaces Affected

- `[state_config.pi_agent]` and `[state_grants.pi_agent]` (docs/DESIGN.md section 3, Planned Pi profile), the Pi adapter, the Pi release notes, `README.md`, and docs/DESIGN.md sections 3 (Credentials) and 15.
- Out of scope: OMP, whose logins are in `agent.db`, which stays writable (its documented limitation); OpenCode, whose `auth.json` is in its writable data folder.

## Acceptance Criteria

- The step 10c expected-failure case records the exact message and which Pi login providers it affects.
- docs/DESIGN.md section 15 records the decision with the alternative not taken and its cost.
- With (a) or (b): a Pi OAuth login refreshes inside a session; `auth.json` stays write-denied, a `!` key cannot be written from a session, and the writable store holds only tokens.
- With (c): the release notes and `README.md` give the steps to log in and refresh outside the guard, and whether `/login` works inside a session.

## How to Verify

- In a disposable home with a Pi OAuth login whose access token has expired, start Pi guarded and send one prompt. With (a) or (b) it succeeds and `auth.json` is unchanged; with (c) it fails with the recorded message, and the documented steps outside the guard restore the login.

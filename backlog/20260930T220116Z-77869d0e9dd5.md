# Write a state file per launch instead of a shared rules.json

## Description

Replace the shared `state/rules.json` with one state file per launch, so each plugin reads the rules of the profile its own launch applied (docs/DESIGN.md section 2, State row). Today a second launch can overwrite the file between the first launch's profile generation and its plugin start; Seatbelt still enforces the first profile, but its plugin refuses or reports against the second launch's rules. Built once, in the Rust launcher.

## Scope / Surfaces Affected

- Rust launcher: write `state/<harness>-<launch-id>.json` atomically before `sandbox-exec`, pass its path to the harness in an environment variable (proposed `AGENT_GUARD_STATE`), and remove state files of ended launches.
- `profiles/opencode/plugin.js`: read the passed path instead of `state/rules.json`.
- Conformance tests, and docs/DESIGN.md sections 2 and 12.
- Out of scope: the zsh engine, which keeps the shared file; `@project` (step 10).

## Acceptance Criteria

- When launch B starts after launch A's profile is generated, A's plugin reports A's rules and B's plugin reports B's.
- The plugin accepts only a regular file directly inside the engine's `state` folder. When the variable points elsewhere or at a symlink, the plugin refuses file-changing tools with a message to relaunch.
- When the state file is missing or malformed, the plugin refuses file-changing tools with a message to relaunch, as it does today when `rules.json` is unreadable.
- A child process started inside the guard inherits the same state path and gets the same rules.
- Cleanup at launch removes only files whose launch has ended. A file still used by a running launch or its children is kept, and a reused process ID does not make an ended launch look alive.
- The state folder stays write-protected from inside the guard, so an agent cannot change or delete its own state file.
- Rolling back to a release without this change restores that release's plugin, which reads the shared file.

## How to Verify

- Conformance test: generate state for launch A, change the Guard List, generate state for launch B, then start A's plugin with A's path. It reports A's rules.
- Start the plugin with the variable unset, pointing outside the state folder, at a symlink and at a malformed file. Each case refuses file-changing tools with the relaunch message.
- Start two guarded launches and end one. At the next launch the ended launch's file is removed and the running one's is kept.
- Inside the guard, try to write, delete and rename the launch's own state file. Each is denied.

# Replace rules.json with a per-launch snapshot and split the plugin

## Description

Replace the shared `state/rules.json` with an immutable snapshot per launch, so each plugin reads the rules of the profile its own launch applied (docs/DESIGN.md section 7, Per-launch snapshot). Today a second launch can overwrite the file between the first launch's profile generation and its plugin start; Seatbelt still enforces the first profile, but its plugin refuses or reports against the second launch's rules. Built once, in the Rust launcher.

In the same step the plugin splits into a shared core and an OpenCode adapter that keeps cc-safety-net's OpenCode entry intact, with no change to OpenCode's behavior (docs/DESIGN.md section 5, Plugin core and adapters; The cc-safety-net compatibility wrapper).

## Scope / Surfaces Affected

- Rust launcher: compile the snapshot from the resolved request and write `state/launch/<profile>-<launch-id>.json` atomically in the execute stage, before `sandbox-exec`; pass its path in `AGENT_GUARD_STATE`; remove snapshots of ended launches; stop writing `state/rules.json`.
- `plugin/core.mjs` and `plugin/opencode.js`, replacing `profiles/opencode/plugin.js`; the installer's plugin link, the `check-config` link, the stamp and release packaging.
- Conformance tests, and docs/DESIGN.md sections 2, 5 and 7.
- Out of scope: the zsh engine, which keeps the shared file; `@project` (step 10a); snapshot fields only Pi needs (step 10c); the Pi adapter (step 10d).

## Acceptance Criteria

- When launch B starts after launch A's profile is generated, A's plugin reports A's rules and B's plugin reports B's.
- The snapshot holds what OpenCode needs now: profile, release ID, launch ID and snapshot version; the plugin projection (allow, read-only and deny sets, and the protected prefixes and name patterns the plugin checks today); the checker chain, `["cc-safety-net"]`. It is written once, under a temporary name and then renamed into place, and is never rewritten.
- `AGENT_GUARD_STATE` carries only the snapshot's location. No rule, path set or checker setting travels in the environment.
- The plugin accepts only a regular file directly inside the engine's `state/launch/` folder. When the variable points elsewhere or at a symlink, the plugin refuses file-changing tools with a message to relaunch.
- When the snapshot is missing, malformed or of an unknown version, the plugin refuses file-changing tools with a message to relaunch, as it does today when `rules.json` is unreadable.
- A child process started inside the guard inherits the same snapshot path and gets the same rules. A nested `opencode` launch that runs directly writes no snapshot and leaves `AGENT_GUARD_STATE` as the enclosing launch set it. Inside a session started from a release before this change, which has no snapshot, a nested `opencode` still runs directly (docs/DESIGN.md section 7, Nested launch).
- A snapshot of another profile than the adapter's counts as unguarded: tools outside the safe set are refused with the relaunch message.
- Cleanup at launch removes only snapshots whose launch has ended. A snapshot still used by a running launch or its children is kept, and a reused process ID does not make an ended launch look alive.
- The state folder stays write-protected from inside the guard, so an agent cannot change or delete its own snapshot.
- `check staged` writes no snapshot, as it writes no `rules.json` today.
- `plugin/core.mjs` holds the release handover, the probe, snapshot reading, path decisions, unguarded refusal, the checker chain and the status text. `plugin/opencode.js` holds OpenCode's hook, its tool-to-operation mapping (including `list`), its safe set and the compatibility wrapper. `core.mjs` imports nothing from the adapter or the vendored code.
- The compatibility wrapper keeps the vendored cc-safety-net OpenCode entry intact. Its `config` hook is forwarded, its other hooks are composed with Agent Guard's as today, and only its `tool.execute.before` runs in the checker chain, after the core's path checks. The environment handling (unset `CC_SAFETY_NET_HOME`, `CC_SAFETY_NET_WORKTREE`, `SAFETY_NET_WORKTREE`; set `CC_SAFETY_NET_PARANOID_RM=1`) moves into it unchanged.
- The 79 plugin checks of `test/plugin.mjs` pass unchanged against the split plugin, and the step 2 checks pass.
- `~/.config/opencode/plugins/agent-guard.js` links to `$engine/current/plugin/opencode.js`, and `check` finds the status tool through it.
- Sessions started from the release before this change keep working after the update. The split plugin hands over to that release's `profiles/opencode/plugin.js`, and `state/rules.json` stays until cleanup removes the last release that reads it.
- Rolling back to a release without this change restores that release's plugin, which reads the shared file.

- Once every Mac runs a release with the snapshot and no session started before it can remain, the launcher refuses a confined launch with `AGENT_GUARD_SANDBOXED=1` and no snapshot (docs/DESIGN.md section 7, Nested launch). Moved here from the retirement item (20260930T220118Z-2a70ad42dffb), which now retires the old projects before step 8.

## How to Verify

- Conformance test: generate state for launch A, change the Guard List, generate state for launch B, then start A's plugin with A's path. It reports A's rules.
- Start the plugin with the variable unset, pointing outside `state/launch/`, at a symlink, at a malformed file and at a snapshot of an unknown version. Each case refuses file-changing tools with the relaunch message.
- Start two guarded launches and end one. At the next launch the ended launch's snapshot is removed and the running one's is kept.
- Inside the guard, try to write, delete and rename the launch's own snapshot. Each is denied.
- `zsh test/test.sh` against the Rust engine passes, and `git diff` shows no check in `test/plugin.mjs` changed or removed.
- Compare the hooks `plugin/opencode.js` returns with those the vendored entry returns: every vendored hook is present, and `config` reaches the vendored entry.
- With an OpenCode server started from the release before this change, update. A new session in that server reports the previous release and enforces its rules.

# Give each launch its own rules file

## Description

Every launch writes the rules it applied to the shared `state/rules.json`, and each session's plugin reads that file. A second launch can overwrite it between the first launch's profile generation and its plugin start; Seatbelt still enforces the first profile, but the first session's plugin then refuses or reports against the second launch's rules. Each launch writes its own rules file and passes that file's path to its plugin, on the zsh engine (docs/DESIGN.md section 12, step 9; decision D12).

## Scope / Surfaces Affected

- `engine/launch`: write the rules to `state/launch/<profile>-<launch-id>.json`, under a temporary name renamed into place, and export its path in `AGENT_GUARD_STATE`; remove files of ended launches at launch.
- `profiles/opencode/plugin.js` and the Grok and Pi readers of the rules, if any: read the file `AGENT_GUARD_STATE` names.
- `check staged`: writes no rules file, as today.
- Out of scope: the typed policy model, plugin split and composition of the original step 9 (decision D12).

## Acceptance Criteria

- When launch B starts after launch A's profile is generated, A's plugin reports and enforces A's rules and B's plugin B's.
- `AGENT_GUARD_STATE` carries only the file's location. The plugin accepts only a regular file directly inside the engine's `state/launch/` folder; when the variable is unset, points elsewhere or at a symlink, or the file is missing, malformed or of an unknown version, the plugin refuses file-changing tools with a message to relaunch.
- A child process started inside the guard inherits the same path. A nested launch that runs directly writes no file and leaves `AGENT_GUARD_STATE` as set.
- Cleanup at launch removes only files whose launch has ended; a reused process ID does not make an ended launch look alive.
- The state folder stays write-protected from inside the guard.
- Sessions started from the release before this change keep working after the update, and `state/rules.json` stays until no installed release reads it.
- In the release after this one, whose notes tell users to restart sessions started before it, the launcher refuses a confined launch with `AGENT_GUARD_SANDBOXED=1` and no rules file.

## How to Verify

- Generate state for launch A, change the Guard List, generate state for launch B, then start A's plugin with A's path: it reports A's rules.
- Start the plugin with the variable unset, pointing outside `state/launch/`, at a symlink, at a malformed file and at an unknown version: each refuses file-changing tools with the relaunch message.
- Start two guarded launches and end one: at the next launch the ended launch's file is removed and the running one's kept.
- `zsh test/test.sh` and `node test/golden.mjs` pass.

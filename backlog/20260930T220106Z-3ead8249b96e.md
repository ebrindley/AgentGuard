# Run the existing checks through an engine adapter

## Description

Put an engine adapter between the existing checks and the zsh launcher so the same checks can run against the Rust launcher at step 8. Keep the v1.0.3 golden fixtures unchanged, and keep the development conformance tests apart from the small check that ships with the install. Nothing the installer copies changes, so runtime behavior stays the same.

## Scope / Surfaces Affected

- New: one adapter per engine under `test/engines/`. This step adds only `test/engines/zsh.mjs`. It can be imported from Node and run as a command from zsh, the same way `test/fixture-home.mjs` is used today.
- Changed: `test/test.sh` and `test/golden.mjs` call the engine only through the adapter. `test/fixture-home.mjs` is called only by the zsh adapter, or folded into it.
- Unchanged: `test/plugin.mjs`. It drives the installed plugin, not the engine.
- The adapter provides four things:
  - `stage`: copy `engine/`, `profiles/` and `install.sh` into the disposable source tree, then apply the test-only home injection to the copy. The zsh adapter does what `test/test.sh` does today: `/bin/cp -R`, then the `fixtureHome` substitution of the `account_home` line in the copied `engine/launch`.
  - `launcher`: the argv that runs the installed launcher. For zsh this is `/bin/zsh "$engine/launch"`, which is what the shebang already runs. Shims such as `$engine/bin/opencode` are still called directly, because users run them.
  - `identity`: run the engine's real account lookup with spoofed `HOME` and `USER`, and return the resolved home and engine folder. The zsh adapter keeps today's method: evaluate the part of `engine/launch` before `source "$profile_dir/harness.zsh"`.
  - `name`: printed once in the suite header.
- Engine selection: `--engine NAME` on both `test/test.sh` and `test/golden.mjs`, defaulting to `zsh`. A flag rather than an environment variable, so the choice does not leak into the launcher and harness under test.
- The v1.0.3 reference in `test/fixtures/opencode-guard-1.0.3/` does not go through the adapter. It is run unmodified with `HOME` set, as today, because v1.0.3 takes its home from `$HOME`.
- `README.md` test section: engine selection, and the split described below.
- The split, recorded in the README and matching docs/DESIGN.md section 8:
  - The development tests are `test/golden.mjs`, `test/test.sh` and `test/plugin.mjs`, and later the conformance suite. They run from a checkout, in a disposable home, outside any agent sandbox, and need Node and the OpenCode CLI. They are not installed and the installer does not run them.
  - The installed check is `launch check`: protected write denied, temp write allowed, `open` denied, then the profile's `check_hook`. For OpenCode that hook confirms `opencode_guard_status` is visible through `opencode serve`. Step 4 adds it as `agent-guard doctor`, under that permanent name (docs/DESIGN.md section 8).
  - The development tests may read the installed check's output, as `test/test.sh` does with `ok   plugins loaded in OpenCode`. The installed check never depends on `test/`.
- Out of scope:
  - Any change to `engine/`, `profiles/`, `install.sh` or `test/fixtures/`.
  - New checks: the Rust adapter and its test-only home injection (step 8, docs/DESIGN.md section 7); Pi suites (step 10); plugin-load and package-store checks (step 7).
  - Renaming shared identifiers (step 3).
  - The `doctor` command, and making a failed self-test fail the install (step 4).

## Acceptance Criteria

- The files in `test/fixtures/opencode-guard-1.0.3/` are byte-identical to the step 2 base commit.
- `engine/`, `profiles/` and `install.sh` are byte-identical to the step 2 base commit. The home injection exists only in the staged copy.
- `node test/golden.mjs` prints the same 3 `ok` lines as before, in the same order:
  - the account lookup check;
  - the `empty` profile comparison;
  - the `nested` profile comparison.
- Golden normalization is still only the two `replaceAll` calls (`OpenCodeGuard` and `OpenCode Guard`).
- `zsh test/test.sh` prints the same check names as on the base commit, in the same order, with the same `ok   `/`FAIL ` prefixes and the final `N failure(s)` line: 72 at stage 1, 76 if step 3's port of OpenCode Guard's later fixes landed first. It exits 0 only when that count is 0.
- Passing `--engine zsh` gives the same output as the default.
- When `--engine` names an engine with no adapter, either script exits non-zero and names the known engines. It runs no checks, creates no install and leaves no `test/.run-*` folder.
- When the zsh adapter cannot find the unique `account_home` seam in the copied launcher, the suite exits non-zero before any check runs, as `fixtureHome` does today.
- Outside `test/engines/`, `test/test.sh` and `test/golden.mjs` contain no engine-source handling: no `fixtureHome`, no slicing of launcher source, no `/bin/zsh "$engine/launch"`.
- After the install in `test/test.sh`, the engine folder holds no file copied from `test/`.
- `launch check` output and exit status are unchanged.
- The README's test section states how to select an engine, and which checks are development conformance and which are installed.

## How to Verify

- `git diff --exit-code <step 2 base> -- test/fixtures engine profiles install.sh` prints nothing and exits 0.
- Outside any agent sandbox, run `node test/golden.mjs` and `zsh test/test.sh` on the base commit and again on the change. Keep only lines starting with `ok  ` or `FAIL`. The two outputs are identical and end with `0 failure(s)`.
- `zsh test/test.sh --engine zsh` matches the default run.
- `zsh test/test.sh --engine none` and `node test/golden.mjs --engine none` both exit non-zero with no `ok` lines. `ls test/.run-*` then finds nothing new.
- `grep -nE 'fixtureHome|indexOf\(|/bin/zsh "\$engine/launch"' test/test.sh test/golden.mjs` finds nothing. The same patterns appear only under `test/engines/`.
- Read the README test section against the split above.

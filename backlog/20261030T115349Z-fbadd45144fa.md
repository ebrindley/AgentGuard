# Add Git-hook protection to Grok

## Description

## Description

Pi sessions cannot write the project's active Git hooks; Grok sessions can, and so can OpenCode sessions until 20261002T015753Z-acbfd918e9f9. A hook written inside a session runs outside the guard at the operator's next Git command in that project. Add the same protection to the Grok profile on the zsh engine (decision D12), sharing the launcher code the OpenCode hooks release adds.

## Scope / Surfaces Affected

- `profiles/grok/harness.zsh` and `engine/launch`: resolve the active Git hooks at launch as Pi's preamble does (`resolve_active_hooks` in `profiles/pi/sandbox/pi-sandbox-preamble.zsh`: `git rev-parse --git-path hooks`, canonicalized, refusing paths broad enough to deny the project or a shared root) and deny writes to them, to `.git/hooks` and to submodule hooks under `.git/modules`.
- docs/DESIGN.md section 3 (Git hooks), SECURITY.md and USAGE.md: what stops working inside Grok sessions.
- Golden fixtures: the change recorded as a difference.
- Out of scope: configuration pivots such as `git config core.hooksPath` (the checker's deny, decision D13) and replacing the default hooks folder, which stay documented limitations as for Pi.

## Acceptance Criteria

- Inside a Grok session, the active Git hooks as resolved at launch, `.git/hooks` and submodule hooks cannot be written, created or replaced; `git init` and `git clone` into a granted folder still work.
- A custom `core.hooksPath` and a linked worktree resolve to their real hooks folder.
- A hooks path that resolves to `/`, the project or a shared root refuses the launch.
- The release notes state what stops working inside Grok sessions.
- `node test/golden.mjs` passes with the recorded difference only.

## How to Verify

- Disposable-home tests under the real `sandbox-exec` in `test/grok.mjs`: writes to each hook path refused, for the default, a custom `core.hooksPath`, a linked worktree and a submodule; `git init` succeeds.

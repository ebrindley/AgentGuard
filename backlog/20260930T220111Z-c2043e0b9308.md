# Migrate OpenCode Guard installs to Agent Guard with tested recovery

## Description

Teach the installer to replace an OpenCode Guard install (v1.0.0 or later) with Agent Guard on the zsh engine, so the two existing installs, a home Mac and a work Mac, can switch at step 6. The switch must never leave an `opencode` command or app that starts OpenCode unguarded, must never have both guards' plugins loaded, and must keep the user's original permission values restorable. The rules are docs/DESIGN.md section 10.

## Scope / Surfaces Affected

- Installer (`profiles/opencode/install.sh` or wherever step 4 puts the OpenCode install logic): a migration part that runs when an OpenCode Guard install is detected. Its phases, in order, are detection, record import, list import, the switch and retirement. Step 4's refusal of an OpenCode Guard install is replaced by this migration.
- Forwarder removal: the switch records its time in Agent Guard's state folder. The first `update` that finds the Mac's boot time later than that time removes the forwarders and the folder `~/Library/Application Support/OpenCodeGuard` that holds them, since no shell started before the switch can remain. `uninstall` also removes them. Neither ever removes `~/OpenCode Guard`. Boot time is `sec` from `/usr/sbin/sysctl -n kern.boottime` (`{ sec = N, usec = M } …`). If the command fails or the output does not parse, the forwarders stay.
- `engine/profile.sb` and `profiles/opencode/plugin.js`: add `~/Library/Application Support/OpenCodeGuard` to the protected paths. Today nothing makes it writable unless an ALLOW entry covers it, and such an entry passes the list checks, which refuse only entries that are or contain `~/Library/Application Support` (docs/DESIGN.md section 4). The explicit rule protects the forwarders as launch links (docs/DESIGN.md section 10, rule 7) and lets the plugin report the path as protected.
- `test/golden.mjs`: compares against the unchanged v1.0.3 fixtures plus this step's recorded, reviewed difference for that rule (docs/DESIGN.md section 8).
- New migration tests under `test/`, run through step 2's engine adapter. They include a real install made by OpenCode Guard's own installer in a disposable home, from the latest OpenCode Guard release at that time and, if step 6's fact collection finds a Mac on a different build, from that build too. The newest tag today is v1.0.4, which is v1.0.3 plus the five fixes ported at the start of step 3. Tests must not depend on a sibling checkout, so each tested tree is stored as a fixture. After step 3's port, `engine/vendor/` matches v1.0.4's `vendor/` but not v1.0.3's (cc-safety-net 2.4.6), so a v1.0.3 fixture carries its own copy.
- `README.md`: moving from OpenCode Guard, what stays in `~/OpenCode Guard`, when the forwarders go, and the way back.
- OpenCode Guard's installed files, as listed in docs/DESIGN.md section 10. Each has a fixed path, with no version stamp.
- Out of scope:
  - Permanent names and the launcher's shim skipping (step 3).
  - The one-liner, staged install, self-test failure handling, the version stamp and the `doctor`, `update` and `uninstall` commands themselves (step 4).
  - Switching the two Macs (step 6), and OpenCode Guard's final release (step 11).
  - Changes to the OpenCodeGuard repository.

## Acceptance Criteria

Detection and preconditions:
- An install counts as OpenCode Guard when any of these exist: OpenCode Guard's `launch`, its permission record, its plugin, its app, its rulebook or a PATH block. The folder `OpenCodeGuard/bin` alone does not count, because after migration it holds Agent Guard's forwarders. So a rerun after a finished migration finds no OpenCode Guard install.
- When none of those exist but `~/OpenCode Guard/Guard List.txt` does, and `~/Agent Guard/Guard List.txt` does not, the Mac held OpenCode Guard before: an uninstall ran, or v1.0.0's uninstall failed a restore and deleted the engine with its record. The installer runs a fresh install with the list import (rule 4) and reports that no permission record exists, so any values OpenCode Guard wrote cannot be restored, naming the OpenCode config files.
- Run from inside either guard, the installer refuses before any change (docs/DESIGN.md section 10, rule 1).
- The migration never runs `~/Library/Application Support/OpenCodeGuard/uninstall.sh`. The old uninstaller would reset the permission values Agent Guard relies on, and v1.0.0's copy deletes the record even when a restore fails.
- While an OpenCode process is running, the installer stops before changing anything and names the process to quit. A server or app started before the switch (`opencode serve`, the desktop app) keeps OpenCode Guard's Seatbelt profile. Each new session it opens rescans the plugin folder and rereads the state file, so after the switch it would enforce Agent Guard's plugin rules under OpenCode Guard's profile, and after retirement a cached OpenCode Guard plugin finds its state folder gone and refuses every tool. Processes checked: `opencode`, the app's `CFBundleExecutable` (`OpenCode`) and `OpenCode Helper`, each with `pgrep -x`. Status 0 stops, 1 continues, and any other status (3 when processes cannot be listed) stops with a message to run outside any sandbox.
- When a startup file has an old start marker without an end marker, the installer stops before the switch and names the file.

Permission record import (docs/DESIGN.md section 10, rule 3):
- OpenCode Guard's `state/permissions.json` is copied into Agent Guard's record before any permission write, keeping `orig` and `wrote` for each config file and key (`edit`, `bash`, `external_directory`).
- A key whose current value equals `wrote` needs no write, because Agent Guard writes the same allow values. A key whose current value differs was changed by the user after OpenCode Guard's install: the installer leaves it as it is and reports it. Values are compared as JSON, so key order does not matter. A config file with no entry in the record is also left as it is and reported. The migration therefore writes no permission value, and undoing a switch needs no permission restore.
- Uninstall restores only values still equal to `wrote`, so user edits survive, and keeps the record as recovery data if a restore fails.
- A copy of OpenCode Guard's record, unchanged, is kept in Agent Guard's state folder until uninstall.
- A `permissions-backup.json` in `~/OpenCode Guard` means an earlier uninstall failed to restore. The installer reports it and does not merge it.
- Without a record, the originals are lost. The installer says so, names the config files and does not claim to restore them.
- When OpenCode Guard's record is unreadable or not an object of per-file entries, the installer exits non-zero before any change. The message names the file, and OpenCode Guard keeps working.
- A config file that already has an entry in Agent Guard's record is not imported again.

List import (docs/DESIGN.md section 10, rule 4):
- When `~/Agent Guard/Guard List.txt` does not exist and `~/OpenCode Guard/Guard List.txt` does, the installer shows, once, both paths and the entries under ALLOW, READ ONLY and DENY, and says the old file is no longer read after the switch. It copies the old list byte for byte only after the user confirms. If the user declines, the installer stops before the switch and changes nothing.
- An existing `~/Agent Guard/Guard List.txt` is never changed by the import. If it differs from the old list, the installer prints both paths and says the old list was not imported.
- `--projects DIR` still adds DIR under ALLOW after the import, with today's rules.

Switch (docs/DESIGN.md section 10, rules 2, 5, 6 and 7):
- Before the switch:
  - Agent Guard is fully staged.
  - The Seatbelt part of its `doctor` has passed through its own launcher.
  - `plugin.js` is outside `~/.config/opencode/plugins`, and Agent Guard's PATH block is not written.
  - No file in OpenCode Guard's install has changed.
- The switch actions:
  - forwarders at `OpenCodeGuard/bin/opencode` and `OpenCodeGuard/bin/opencode-gui`, each put in place with one rename;
  - the plugin swap: Agent Guard's plugin link is renamed onto `opencode-guard.js`, then renamed to `agent-guard.js`, so the folder never holds both plugins and never holds neither;
  - Agent Guard's PATH block replacing OpenCode Guard's in each startup file, one file at a time. Each file is rewritten through a temporary file, and a symlinked startup file is edited at its target, as today;
  - Agent Guard's app, with its own bundle ID from step 3, replacing `OpenCode Guard.app`;
  - Agent Guard's rulebook and `rule.json` entry;
  - the switch time, recorded last.
- Each forwarder is a symlink to Agent Guard's shim of the same name. The shim's `${0:A:h:h}` therefore resolves through `bin` and `current` to the active release folder, `releases/<id>`, whose `launch` it runs.
- Before each action, every file it changes or removes is copied to a migration backup, and each finished action is written to a journal in Agent Guard's state folder.
- The invariants below hold after every switch action, as well as at the end:
  - The plugin folder never holds both plugins.
  - Every entry point either runs OpenCode under a Seatbelt profile or refuses to start. The entry points are the old shim paths, Agent Guard's shims, the old app and the new app.
- Before the switch, the staged check loads the staged plugin with `XDG_CONFIG_HOME` pointing into the staged release. Right after the plugin swap, the same check runs against `~/.config/opencode/plugins` and must see Agent Guard's status tool and no `opencode-guard.js`.
- When any switch action or that check fails, the installer undoes the finished actions in reverse from the backup and exits non-zero. OpenCode Guard's files are then byte-identical to before the switch and OpenCode Guard launches.
- A run that finds a journal from an interrupted switch resumes it from the journal and finishes the switch (docs/DESIGN.md section 10, rule 11).
- The switch output says to replace a Dock item for the old app with Agent Guard.app.

Retirement (docs/DESIGN.md section 10, rules 9 and 10):
- After `doctor` passes and OpenCode launches through the new command path and a forwarder, retirement removes OpenCode Guard's rulebook, its `opencode-guard` entry in `rule.json`, the migration backup, and the old engine's `launch`, `profile.sb`, `uninstall.sh`, `vendor/` and `state/`, the last only once the imported record is written and read back. The two forwarders stay. The entries OpenCode Guard added to `transparent_wrappers` stay, as its own uninstaller leaves them.
- `~/OpenCode Guard` stays. Retirement adds one note file there naming the new list.
- When `rule.json` cannot be changed, the old rulebook and its entry stay, and the installer warns.
- A retirement failure leaves Agent Guard active and exits non-zero. A rerun finishes retirement.

Forwarder removal:
- `update` with a boot time earlier than the recorded switch time leaves the forwarders. With a later boot time it removes them and `~/Library/Application Support/OpenCodeGuard`, also when the install is already current. `uninstall` removes them either way.
- After removal, no OpenCode Guard file remains outside `~/OpenCode Guard`.

Recovery matrix (all automated, disposable home, outside any agent sandbox):
- Real install: each tested OpenCode Guard build is installed by its own installer and has a user-edited config. Migrating it gives:
  - Agent Guard's plugin as the only guard plugin;
  - forwarders at both old command paths;
  - Agent Guard's PATH blocks only;
  - Agent Guard.app with the new bundle ID, and no `OpenCode Guard.app`;
  - the imported record and the recorded switch time.
  - Then `uninstall` restores the pre-OpenCode-Guard values, keeps the values the user changed after OpenCode Guard's install, and removes the forwarders and the old engine folder.
- Before the switch: a failure is injected at each phase, including a failed Seatbelt check and a declined list import. The installer exits non-zero, OpenCode Guard's files are byte-identical, the plugin folder holds only `opencode-guard.js`, and a launch through the old shim runs under OpenCode Guard, whose own `launch check` passes.
- During the switch: a failure is injected after each switch action and after the plugin-load check. The installer exits non-zero, the state equals the pre-switch state, and OpenCode Guard launches. A run killed after each action leaves both invariants true, and the next run resumes and completes the switch.
- After the switch: a retirement failure is injected, for example an unwritable `rule.json`. Agent Guard stays active, the exit code is non-zero, and a rerun finishes retirement with no second import.
- The way back: after the switch, `uninstall` followed by the same OpenCode Guard build's installer gives a working OpenCode Guard. Its record's `orig` values are the pre-guard values.
- v1.0.0 restore failure: a v1.0.0 uninstall failed a restore and deleted the record, so the configs hold the guard's allow values and only `~/OpenCode Guard` remains. The installer imports the list, does not invent originals, and prints that the original permission values could not be recovered, naming the config files.
- A failed uninstall of v1.0.1 or later left `permissions-backup.json`: the installer reports it and does not merge it.
- A config cannot be parsed at Agent Guard's uninstall: the uninstall keeps the record as recovery data and exits non-zero.
- User-edited permissions: keys changed, added or removed after OpenCode Guard's install are left as they are. After uninstall the result equals what OpenCode Guard's own uninstaller would have given.
- Reruns: a rerun after a finished migration changes nothing:
  - no second import;
  - the list output does not appear again;
  - the forwarders, the switch time and the record are unchanged;
  - the permission files are byte-identical.
  - A rerun after each injected failure ends in the same state as an uninterrupted run.
- Already open terminal: a shell whose PATH was set by OpenCode Guard's block before the switch runs `opencode` after the switch. The forwarder then runs Agent Guard's launcher under Seatbelt, with a fake harness recording that it was sandboxed, and finishes without recursion within the test timeout. The same holds with OpenCode Guard's and Agent Guard's `bin` folders both on PATH in either order.
- Unfinished block: a startup file with an old start marker and no end marker stops the installer before the switch, with the file named and nothing changed.
- Forwarder removal: with the boot time set in the test before and after the recorded switch time, `update` keeps and then removes the forwarders.

## How to Verify

- `zsh test/test.sh` and `node test/golden.mjs` through the zsh adapter, outside any agent sandbox. Step 2's checks still pass. The golden test matches the v1.0.3 fixtures plus this step's recorded difference, the rule protecting `~/Library/Application Support/OpenCodeGuard`.
- Run the migration test. Each matrix case prints an `ok` line and the run ends with `0 failure(s)`. Each case asserts the files named in its criterion, and asserts that `~/.config/opencode/plugins` never lists both plugins.
- For the byte-identical cases, compare `shasum` of every OpenCode Guard file, startup file and config file before and after.
- `grep -rn 'OpenCodeGuard/uninstall.sh' profiles engine` finds no call to the old uninstaller.
- Manually, on a disposable account or VM with a real OpenCode Guard install of the latest release:
  - Open a terminal, run the installer from another terminal, and then run `opencode` in the first terminal. It is guarded.
  - Open Agent Guard.app. It is guarded.
  - `agent-guard doctor` passes.

## Dependencies

- Step 2 (Test contract): the engine adapter the migration tests run through.
- Step 3 (Permanent names on the zsh engine): Agent Guard's own plugin file, markers, rulebook, status tool and bundle ID (docs/DESIGN.md section 10, rule 6), and the launcher skipping every guard shim, old and new (rule 8). Without the skip, the forwarders and the old shims recurse.
- Step 4 (Installer: install, update, uninstall): staged install, `doctor`, self-test failure handling and the `update` and `uninstall` commands this step extends.

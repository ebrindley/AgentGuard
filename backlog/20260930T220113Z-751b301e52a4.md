# Protect OpenCode's npm package store from writes inside the guard

## Description

Write-protect OpenCode's npm package store, which OpenCode Guard v1.0.3 leaves writable through its `~/.cache` grant, so an agent cannot change plugin code that OpenCode imports at the next start. This is the first policy update after the switch and reaches both Macs through `update`.

## Scope / Surfaces Affected

- `profiles/opencode/harness.zsh`: the current store `<cache>/opencode/packages` and the legacy `<cache>/opencode/node_modules` with its install metadata become protected paths. Their ancestors inside the writable cache are pinned against rename and removal only, as the list pins folders above a DENY entry (docs/DESIGN.md section 4). The rest of the cache stays writable.
- `engine/launch`: resolve the effective cache root from `XDG_CACHE_HOME` at launch, falling back to `~/.cache`. Today the engine hard-codes `~/.cache` and does not read `XDG_CACHE_HOME`.
- `agent-guard doctor` (step 4) and `opencode_check`: check that each configured plugin loaded, not only the guard's status tool.
- Conformance tests (docs/DESIGN.md section 8). The golden test compares against the unchanged v1.0.3 fixtures plus the recorded, reviewed differences of step 5 and this step.
- `README.md` and docs/DESIGN.md section 9: operator maintenance for plugins and npm language servers.
- Out of scope: freezing all of `~/.cache` or the whole OpenCode cache, loaded-code integrity checks and plugin maintenance from inside the guard.

## Acceptance Criteria

- When a guarded process writes, creates, deletes, renames or replaces anything in the current, legacy or `XDG_CACHE_HOME`-relocated store, the write is denied. This includes the store folder itself and symlinks planted in it.
- When a guarded process renames or replaces an ancestor of the store inside a writable root (`~/.cache/opencode` or `~/.cache` at the default location), the write is denied.
- An ALLOW entry that covers a relocated store does not reopen it: the store rules come after the list rules (docs/DESIGN.md section 3).
- Writes elsewhere in the cache, including other files in `<cache>/opencode`, still succeed.
- With a pre-populated store, configured npm plugins load and a representative npm language server (TypeScript) starts inside the guard.
- When a configured plugin or language server is missing from the store, the user sees a message that names the package and points to the maintenance procedure. OpenCode starting is not treated as success.
- When a configured plugin fails to load, `doctor` fails and names it.
- The maintenance procedure states that it runs outside the guard with full authority.
- The v1.0.3 golden fixtures stay unchanged; this step's recorded difference holds only the store rules.
- Store paths are confirmed against the OpenCode version on both Macs, since the spike tested 1.18.33 only.

## How to Verify

- Run the conformance suite outside any agent sandbox: each store path and ancestor is denied for write, creation, rename and symlink replacement at the default and a relocated cache root; a sibling cache file is writable.
- Run the spike's probe table (docs/DESIGN.md section 9) against the new profile. The five package-store probes that were allowed must now be denied, and the other three must be unchanged.
- In a disposable home with one configured npm plugin and TypeScript files, launch guarded: the plugin's effect is visible and the TypeScript language server responds.
- Remove the plugin's package folder, then launch guarded. The message names the package, and `doctor` exits non-zero naming it.
- Run `update` on a test install of the previous release: the new profile applies and `doctor` passes.

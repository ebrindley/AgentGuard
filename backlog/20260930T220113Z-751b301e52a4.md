# Protect OpenCode's package store, bin folder and model catalog

## Description

Write-protect three parts of OpenCode's cache that OpenCode Guard v1.0.3 leaves writable through its `~/.cache` grant (`<cache>` is `XDG_CACHE_HOME`, else `~/.cache`):

- the npm package store, whose plugin code OpenCode imports at the next start;
- `<cache>/opencode/bin`, which holds ripgrep and language servers that OpenCode runs;
- the model catalog, `<cache>/opencode/models.json` or `models-<hash>.json`. OpenCode reads it before its built-in list. It sets each provider's API address and package, and OpenCode imports `file://` packages directly, so a rewritten catalog can send an API key to another host or load code.

A guarded restart runs changed code under Seatbelt; a later start without the guard runs it with full authority (docs/DESIGN.md section 9). This is the first policy update after the switch and reaches both Macs through `update`.

## Scope / Surfaces Affected

- `profiles/opencode/harness.zsh` and `protected.sb`: the current store `<cache>/opencode/packages`, the legacy `<cache>/opencode/node_modules` with its install metadata, `<cache>/opencode/bin` and the catalog names `models*.json` directly in `<cache>/opencode` become protected. Their ancestors inside the writable cache are pinned against rename and removal only, as the list pins folders above a DENY entry (docs/DESIGN.md section 4). The rest of the cache stays writable.
- `engine/launch`: resolve the effective cache root from `XDG_CACHE_HOME` at launch, falling back to `~/.cache`. Today the engine hard-codes `~/.cache` and does not read `XDG_CACHE_HOME`. Create `<cache>/opencode/bin` before the sandbox applies when it is missing: OpenCode 1.18.34 creates it with its other folders at every start (`packages/core/src/global.ts`), and the deny stops that create.
- `agent-guard doctor` (step 4) and `opencode_check`: check that each configured plugin loaded, not only the guard's status tool.
- Conformance tests (docs/DESIGN.md section 8). The golden test compares against the unchanged v1.0.3 fixtures plus the recorded, reviewed differences of step 5 and this step.
- `README.md` and docs/DESIGN.md section 9: operator maintenance for plugins, npm language servers and the downloads OpenCode keeps in `bin`, and the catalog's refresh. The known limitations in `README.md` and `SECURITY.md`.
- From step 10c these denies are part of the protection union and render in every launch of every installed harness, so Pi's `~/.cache` grant cannot reopen them (step 10 item). This step renders them for OpenCode.
- Out of scope: freezing all of `~/.cache` or the whole OpenCode cache; checking what a store, `bin` or catalog written before this step contains; loaded-code integrity checks; plugin maintenance from inside the guard; the other code in writable folders that gates composition (docs/DESIGN.md section 9; step 10e item).

## Acceptance Criteria

- When a guarded process writes, creates, deletes, renames or replaces anything in the current, legacy or `XDG_CACHE_HOME`-relocated store, or in `<cache>/opencode/bin` at the default or the relocated root, the write is denied. This includes each folder itself and symlinks planted in it.
- When a guarded process writes, creates, deletes, renames or replaces `models.json` or a `models-<hash>.json` in `<cache>/opencode`, at the default or the relocated root, the write is denied, including when no catalog exists yet.
- When a guarded process renames or replaces an ancestor of the store, `bin` or the catalog inside a writable root (`~/.cache/opencode` or `~/.cache` at the default location), the write is denied.
- When `XDG_CACHE_HOME` is set and cannot be resolved to a canonical absolute path, the launch is refused rather than protecting the default location only.
- An ALLOW entry that covers a relocated store, `bin` or catalog does not reopen it: these rules come after the list rules (docs/DESIGN.md section 3).
- Writes elsewhere in the cache, including other files in `<cache>/opencode`, still succeed.
- With a pre-populated store, configured npm plugins load and a representative npm language server (TypeScript) starts inside the guard.
- When `<cache>/opencode/bin` is missing, the launch creates it before the sandbox applies, and OpenCode starts with it present and write-denied.
- With a populated `bin`, its tools work inside the guard: with no `rg` on `PATH`, OpenCode's `grep` and `glob` tools run `<cache>/opencode/bin/rg`, and a language server installed in `bin` starts.
- When a configured plugin or language server is missing from the store, the user sees a message that names the package and points to the maintenance procedure. OpenCode starting is not treated as success.
- When ripgrep is in neither `PATH` nor `bin`, the user sees a message that names it and points to the maintenance procedure. A language server that OpenCode would download into `bin` is skipped by OpenCode without a message when the download cannot be written (OpenCode 1.18.34 `packages/opencode/src/lsp/server.ts`), so the maintenance procedure lists those downloads and `README.md` states that such a server is unavailable inside the guard until it is installed outside it.
- With the catalog locked, OpenCode inside the guard still lists models: from the existing catalog, or from its bundled snapshot when there is none. The test records what the refresh does and what the user sees. From the source, not tested: OpenCode 1.18.34 writes a new catalog to a temporary file beside the old one, renames it into place, and logs and ignores a failure (`packages/core/src/models-dev.ts`). docs/DESIGN.md section 9 and `README.md` state the result and that the catalog refreshes only on a start outside the guard.
- When a configured plugin fails to load, `doctor` fails and names it.
- The maintenance procedure states that it runs outside the guard with full authority.
- The v1.0.3 golden fixtures stay unchanged; this step's recorded difference holds only the rules for the store, `bin` and the catalog.
- The store, `bin` and catalog paths are confirmed against the OpenCode version on both Macs. The spike tested the store on 1.18.33 only; the `bin` and catalog paths come from the 1.18.34 source.

## How to Verify

- Run the conformance suite outside any agent sandbox: each store path, `bin`, each catalog name and each ancestor is denied for write, creation, rename and symlink replacement at the default and a relocated cache root; a sibling cache file is writable.
- Run the spike's probe table (docs/DESIGN.md section 9) against the new profile. The five package-store probes that were allowed must now be denied, and the other three must be unchanged.
- In a disposable home with one configured npm plugin and TypeScript files, launch guarded: the plugin's effect is visible and the TypeScript language server responds.
- Remove the plugin's package folder, then launch guarded. The message names the package, and `doctor` exits non-zero naming it.
- In a disposable home with no `bin` folder, launch guarded: OpenCode starts and `bin` exists afterwards. With `rg` absent from `PATH` and present in `bin`, a `grep` tool call returns matches; with `rg` in neither, the message names ripgrep.
- With a catalog older than five minutes, so that OpenCode tries a refresh, launch guarded: the model list shows the catalog's models, and the catalog's hash and modification time are unchanged afterwards. Record the refresh failure in OpenCode's log. Delete the catalog and repeat: the model list loads from the bundled snapshot and no catalog is created.
- Run `update` on a test install of the previous release: the new profile applies and `doctor` passes.

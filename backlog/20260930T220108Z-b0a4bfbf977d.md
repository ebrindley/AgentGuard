# Replace names shared with OpenCode Guard and define the release

## Description

Give the zsh engine names that OpenCode Guard does not use, fix the launcher loop between the two guards' shims (docs/DESIGN.md section 10, rule 8), and define what a release archive contains. Stage 1 still shares these names with OpenCode Guard, so each installer and uninstaller can change the other's files. This lands after step 3's first change, the port of OpenCode Guard's fixes after v1.0.3.

## Scope / Surfaces Affected

Names shared with OpenCode Guard today (found by grepping `engine/`, `profiles/opencode/` and `install.sh` for `opencode-guard`, `opencode_guard`, `OPENCODE_GUARD`, `ai.opencodeguard`, `OpenCodeGuard`, `last-launch` and `OPENCODE_SANDBOXED`), and the names confirmed here:

| Identifier | Now (same in OpenCode Guard) | Confirmed name | Where |
|---|---|---|---|
| Plugin file | `~/.config/opencode/plugins/opencode-guard.js` | `agent-guard.js` | `profiles/opencode/install.sh`, `uninstall.sh` |
| PATH markers | `# >>> opencode-guard >>>` and `# <<< opencode-guard <<<` | `# >>> agent-guard >>>` and `# <<< agent-guard <<<` | `install.sh`, `uninstall.sh` (profile) |
| Rulebook | folder `~/.cc-safety-net/rules/opencode-guard/`, rulebook `name`, entry in `rule.json` | `agent-guard` for all three (cc-safety-net requires the folder, the `rule.json` source and the rulebook `name` to match) | `templates/cc-safety-net/rules/`, `install.sh`, `uninstall.sh` |
| Status tool | `opencode_guard_status` | `agent_guard_status` | `plugin.js` (tool and unguarded safe set), `hooks.zsh` (both checks) |
| Bypass variable | `OPENCODE_GUARD_BYPASS` | `AGENT_GUARD_BYPASS` | `plugin.js` |
| Launcher message prefix | `opencode-guard:` | `agent-guard:` | `engine/launch` `fail` and `note` |
| Check probe file | `.opencode-guard-check` in the per-user temp folder | `.agent-guard-check` | `engine/launch` |
| App bundle ID | `ai.opencodeguard.launcher` (docs/DESIGN.md section 10, rule 6) | `io.github.ebrindley.agentguard` | `install.sh` |
| Nesting marker | `OPENCODE_SANDBOXED` | `AGENT_GUARD_SANDBOXED` | `engine/launch`, `harness.zsh`, `hooks.zsh` |
| Icon source file | `assets/OpenCodeGuard.icns` | `assets/AgentGuard.icns` (same image) | `profiles/opencode/assets/`, `install.sh` |

- The nesting marker is a guard identifier, not a harness one. `engine/launch` reads it in the engine to decide "already inside the guard", and the profile only sets it through `env_set`. OpenCode does not read it: the OpenCode 1.18.33 binary contains no `OPENCODE_SANDBOXED` string, and neither do the plugin or the vendored cc-safety-net. The engine sets `AGENT_GUARD_SANDBOXED=1` itself for every harness, and `harness.zsh` no longer lists it. Until step 11 the launcher also treats `OPENCODE_SANDBOXED=1` as already guarded, so a session started under OpenCode Guard that reaches the new launcher does not try to apply a second profile.
- Log: not shared, no rename. OpenCode Guard writes `~/OpenCode Guard/last-launch.log`; Agent Guard keeps `~/Agent Guard/last-launch-opencode.log`.
- Already distinct, no change: engine folder `~/Library/Application Support/AgentGuard`, list `~/Agent Guard/Guard List.txt`, app `~/Applications/Agent Guard.app`, plugin export `AgentGuard`, the plugin's "Agent Guard:" messages.
- `next_cli` in `engine/launch` (docs/DESIGN.md section 10, rule 8). Today it skips only a candidate whose resolved path is `${bin:A}/$cli`. It will skip any candidate whose resolved path is inside one of the guard shim folders, which the engine keeps in a single list: `$engine/bin` and `$home/Library/Application Support/OpenCodeGuard/bin`. The `launch check` plugin probe uses `next_cli`, so it gets the same fix. The folder list stays in the engine because guard shims are a guard concern.
- `LICENSE`: the copyright line reads "OpenCodeGuard contributors". Add an Agent Guard contributors line and keep the original, since the code is a port.
- Release contents: a script, `scripts/release.sh <version>`, builds `dist/agent-guard-<version>.tar.gz` and `dist/agent-guard-<version>.tar.gz.sha256` from an explicit file list. Everything sits under one `agent-guard-<version>/` folder:
  - `install.sh`, `LICENSE`, and `VERSION` (written by the script)
  - `engine/launch`, `engine/profile.sb`, and all of `engine/vendor/cc-safety-net` including its `LICENSE`
  - `profiles/opencode/`: `harness.zsh`, `hooks.zsh`, `protected.sb`, `plugin.js`, `opencode`, `opencode-gui`, `install.sh`, `uninstall.sh`, all of `templates/`, and `assets/AgentGuard.icns`
- The installer also copies `LICENSE` into the engine folder, next to the vendored cc-safety-net license it already copies.
- Tests, run through the step 2 engine adapter: update the names in `test/test.sh` and `test/plugin.mjs`. `test/golden.mjs` also clears `AGENT_GUARD_SANDBOXED`. The v1.0.3 fixtures stay unchanged.
- `README.md`: document `AGENT_GUARD_BYPASS=1`, and state that `OPENCODE_GUARD_BYPASS` is no longer honored.
- `docs/DESIGN.md`: sections 2, 3 and 5 describe the built engine, so they change with the renames: the install layout table, the "still OpenCode Guard's" sentence, the `harness.zsh` listing, the plugin's status tool and bypass variable. Section 12's proposed-name table records the confirmed names.
- Out of scope:
  - Publishing the release (step 6); downloading, checksum checks and staging (step 4); detecting and switching an OpenCode Guard install, keeping the new plugin out of the plugin folder, forwarders and their write protection (step 5, docs/DESIGN.md section 10).
  - Moving harness wording in engine messages ("OpenCode needs", "opencode not found") into profile data (step 10).
  - A new icon image.
  - This installer still writes into the live plugin folder, so it must not run on either Mac that has OpenCode Guard installed (docs/DESIGN.md section 10, rules 2 and 3). Step 4's installer refuses such an install until step 5 adds the migration.

## Acceptance Criteria

- `grep -rnE 'opencode-guard|opencode_guard|OPENCODE_GUARD|ai\.opencodeguard|OpenCodeGuard' engine profiles install.sh scripts` prints only the OpenCode Guard shim folder in the engine's skip list. `grep -rn OPENCODE_SANDBOXED engine profiles` prints only the legacy nesting check.
- After install in a disposable home:
  - The plugin is `~/.config/opencode/plugins/agent-guard.js`.
  - `~/.cc-safety-net/rules/agent-guard/rulebook.json` has `"name": "agent-guard"`, and `rule.json` lists `agent-guard`.
  - The shell files contain `agent-guard` markers.
  - `plutil -extract CFBundleIdentifier raw ~/Applications/Agent\ Guard.app/Contents/Info.plist` prints `io.github.ebrindley.agentguard`.
  - The engine folder contains `LICENSE`.
- When `.zprofile` and `.zshrc` already hold an `opencode-guard` block, install and uninstall leave that block byte-for-byte unchanged and change only the `agent-guard` block.
- When `rule.json` lists both `opencode-guard` and `agent-guard`, and both rulebook folders exist, uninstall removes only `agent-guard`. `opencode-guard.js` in the plugin folder is never created, changed or deleted.
- The plugin registers `agent_guard_status`. `launch check` reports "plugins loaded" only when OpenCode's tool IDs include `agent_guard_status`.
- Running unguarded:
  - When `AGENT_GUARD_BYPASS=1` is set, the plugin allows tools.
  - When only `OPENCODE_GUARD_BYPASS=1` is set, the plugin refuses them, as it does with no variable set.
- Shim loop (docs/DESIGN.md section 10, rule 8):
  - Setup: PATH lists `~/Library/Application Support/AgentGuard/bin`, then `~/Library/Application Support/OpenCodeGuard/bin`, then a folder with a stub `opencode`. The old folder holds the v1.0.3 fixture launcher with its shim.
  - When `opencode` runs, the stub runs once under Agent Guard's profile, and the old shim never runs.
  - With the two folders in the opposite order, the stub runs once, and Agent Guard's launcher does not apply a second profile.
  - A regression makes the check fail within a bounded wait instead of hanging.
- A candidate reached through a symlink into either guard shim folder is skipped.
- Outside a sandbox, `AGENT_GUARD_SANDBOXED=1` or `OPENCODE_SANDBOXED=1` does not skip the guard. Inside a guard sandbox, a nested `launch cli` with either marker runs the CLI directly and keeps the child `HOME`. These are the existing checks, run once for each marker.
- `node test/golden.mjs` passes, and `test/fixtures/opencode-guard-1.0.3` is unchanged.
- `scripts/release.sh <version>`:
  - builds an archive whose `tar -tzf` listing matches the file list exactly, with no `test/`, `docs/`, `backlog/`, `.poetic/` or `.DS_Store` entries;
  - builds a `.sha256` file that `shasum -a 256 -c` accepts;
  - writes a `VERSION` file that holds the given version.
- When `install.sh` runs from the unpacked archive in a disposable home, the integration checks pass.
- The archive's license notices cover everything it ships. Check whether cc-safety-net's `dist/` bundles third-party code; if it does, add that code's notices.

## How to Verify

- Run the two `grep` commands above from the repository root. The output is exactly the two expected lines.
- Run `node test/golden.mjs` and `zsh test/test.sh` outside any agent sandbox. They should report 0 failures, including the new checks for marker isolation, the rulebook, the bypass variable, the shim loop in both orders, and the symlinked shim.
- Run `git diff --stat test/fixtures`. The output is empty.
- In the disposable home, run `node "$HOME/Library/Application Support/AgentGuard/vendor/cc-safety-net/dist/bin/cc-safety-net.js" rule verify`. It accepts the `agent-guard` rulebook.
- Run `scripts/release.sh 0.0.0-test`. Then compare `tar -tzf dist/agent-guard-0.0.0-test.tar.gz` with the file list, and run `shasum -a 256 -c dist/agent-guard-0.0.0-test.tar.gz.sha256`.
- Unpack the archive into a temporary folder and run the integration test against that copy.

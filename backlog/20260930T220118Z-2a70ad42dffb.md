# Remove legacy guard files and compatibility markers

## Description

OpenCode Guard and pi-sandbox-guard are deprecated and archived, each with a final recovery release. A migrated install still keeps their retired files and accepts OpenCode Guard's session marker. Add a cleanup step that removes the retired files once their contents are carried over, update uninstall's recovery steps to match, and stop accepting `OPENCODE_SANDBOXED=1`.

Archive, not delete: Agent Guard's docs, golden fixtures and difference records cite both repositories' commits and tags, `profiles/pi/LICENSE` carries pi-sandbox-guard's notice, and the archived repositories stay readable as the recovery path.

## Scope / Surfaces Affected

- A cleanup step that `agent-guard` runs on request (command name decided when built), journaled like the OpenCode Guard retirement. It removes:
  - OpenCode Guard's forwarders and engine folder (`$ocg/bin/opencode`, `opencode-gui`, `~/Library/Application Support/OpenCodeGuard`), through the forwarder removal that already exists (docs/DESIGN.md section 10).
  - `~/OpenCode Guard` (old list, log and permission backup) and `state/opencode-guard-permissions.json`, once the old list's entries are in `~/Agent Guard/Guard List.txt` and the recorded permission values match.
  - `state/legacy/pi-sandbox-guard/` (the retired originals, the launcher stamp, the `~/.local/bin/<name>.bak.*` files and `extension-backups/`), once the bindings and wrappers it recorded are in Agent Guard's state.
- Uninstall: once the legacy bundle is gone, recovery names the archived repository's final tag instead of reinstating from the bundle.
- `engine/launch`: stop treating `OPENCODE_SANDBOXED=1` as already guarded. `AGENT_GUARD_SANDBOXED=1` without a snapshot stays until the per-launch snapshot (20260930T220116Z-77869d0e9dd5).
- docs/DESIGN.md: step 11, section 10 rule 10 ("What stays"), section 11 (The adoption, Uninstall, The Pi migration) and the section 12 end states.
- Out of scope: the migration modules, which stay while users can still migrate from the final releases; any change to OpenCode Guard's or pi-sandbox-guard's behavior.

## Acceptance Criteria

- After cleanup on a migrated install: `~/Library/Application Support/OpenCodeGuard`, `~/Applications/OpenCode Guard.app`, `~/.config/opencode/plugins/opencode-guard.js`, `~/.cc-safety-net/rules/opencode-guard/`, `~/OpenCode Guard`, `state/opencode-guard-permissions.json` and `state/legacy/pi-sandbox-guard/` do not exist. No `opencode-guard` entry in `rule.json` and no `opencode-guard` PATH block remains. `agent-guard doctor` passes, and OpenCode, Pi and OMP start guarded.
- The cleanup refuses, and removes nothing, while a file it would remove holds a list entry, permission value, binding or wrapper that Agent Guard's state lacks, and names what is missing.
- Interrupted at each journaled step and rerun, the cleanup finishes without error. Run again after it finishes, it changes nothing.
- After cleanup, uninstall prints recovery steps whose every named file or tag exists.
- The launcher no longer accepts `OPENCODE_SANDBOXED=1`, and that release's notes say a session started under OpenCode Guard must be restarted.
- docs/DESIGN.md describes this plan.

## How to Verify

- The cleanup step's tests in a disposable home with a migrated OpenCode Guard and pi-sandbox-guard install, interrupted at each journaled step, and with a missing list entry, permission value, binding and wrapper.
- Uninstall in a disposable home after cleanup, checking each recovery step's named file or tag.
- A launch with `OPENCODE_SANDBOXED=1` set applies Agent Guard's profile.

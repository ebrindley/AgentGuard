# Stop accepting OpenCode Guard's session marker

## Description

OpenCode Guard and pi-sandbox-guard are deprecated and archived, each with a final recovery release. The launcher still treats OpenCode Guard's `OPENCODE_SANDBOXED=1` as already guarded. Stop accepting it, so a launch inside an OpenCode Guard session takes the existing path for another tool's sandbox.

Migration already removes OpenCode Guard's app, plugin, PATH blocks, launcher and rulebook entry, and `update` removes its forwarders and engine folder after a boot. The remaining files (`~/OpenCode Guard`, `state/opencode-guard-permissions.json`, `state/legacy/pi-sandbox-guard/`) do not run, cannot be written from sessions, and the Pi bundle is uninstall's way back to pi-sandbox-guard. No cleanup command is built for them.

Archive, not delete: Agent Guard's docs, golden fixtures and difference records cite both repositories' commits and tags, `profiles/pi/LICENSE` carries pi-sandbox-guard's notice, and the archived repositories stay readable as the recovery path.

## Scope / Surfaces Affected

- `engine/launch`: stop treating `OPENCODE_SANDBOXED=1` as already guarded.
- `test/test.sh`: a nested launch with the marker takes the other-sandbox path.
- docs/DESIGN.md: step 11 and the sections that cite it.
- Out of scope: the migration modules, uninstall, and removal of the retired files.

## Acceptance Criteria

- Inside a sandbox, a launch with only `OPENCODE_SANDBOXED=1` set is treated as inside another sandbox: `cli` runs the harness under that sandbox and other modes refuse naming another sandbox.
- Outside a sandbox the marker is ignored, as before.
- The release notes say a session started under OpenCode Guard must be restarted.
- docs/DESIGN.md describes this plan.

## How to Verify

- `zsh test/test.sh` nested-marker checks.

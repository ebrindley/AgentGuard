# Retire OpenCode Guard and pi-sandbox-guard after the Macs migrate

## Description

Retire both earlier projects as soon as every Mac that ran one has migrated to Agent Guard and passed a legacy audit, without waiting for the Rust launcher or Pi's move to the shared engine (steps 8 to 10). On each Mac the audit first proves that every part of the old guard's configuration is carried into Agent Guard. Gaps are filed for improvement. Legacy files and folders are removed only after that, by a journaled step that can be repeated. Then each project gets a final release pointing to Agent Guard, and its repository is archived.

Archive, not delete: Agent Guard's docs, golden fixtures and difference records cite both repositories' commits and tags, `profiles/pi/LICENSE` carries pi-sandbox-guard's notice, and an archived repository stays readable as the recovery path. pi-sandbox-guard is a private npm package and was never published, so there is nothing to deprecate on npm.

This replaces the earlier plan, which archived both projects only at step 11, after the Rust release and step 10d.

## Scope / Surfaces Affected

Macs in scope: every Mac with OpenCode Guard or pi-sandbox-guard installed (the owner's Macs, the work Mac included) and any other Mac migrated in the same round. A Mac with neither old guard gets a fresh install and needs no audit.

### 1. Legacy audit, read-only, on each migrated Mac

Run after the migration and before any cleanup. Each line is recorded as carried over, live under its old name, gap, or not present. Where a check compares content, compare it to the pre-migration copies the migration kept (the legacy bundle, `state/opencode-guard-permissions.json`, `~/OpenCode Guard`).

OpenCode Guard:
- Guard List: every ALLOW, READ ONLY and DENY entry of `~/OpenCode Guard`'s list is in `~/Agent Guard/Guard List.txt`, with the same meaning.
- Permissions: OpenCode config `permission` values (`edit`, `bash`, `external_directory`) equal their pre-switch values in every config file OpenCode Guard recorded. `state/permissions.json` holds OpenCode Guard's `orig` values, so uninstall would restore the user's own values.
- cc-safety-net: `rule.json` has `agent-guard` in `rules` and every `transparent_wrappers` entry it had, and no `opencode-guard`. Any custom rule or `.cc-safety-net/policy.json` the user added still applies.
- Launch routes: `opencode` in a new terminal, Agent Guard's app and any Dock item or alias that started OpenCode Guard's app all start OpenCode guarded. No `# >>> opencode-guard >>>` block remains in `.zprofile`, `.zshrc` or `.bash_profile`.
- Local changes: the retired engine files (launcher, `profile.sb`, vendored code, plugin) are compared with the OpenCode Guard tag they came from. Any difference is a local customization; each is either matched by Agent Guard or filed as a gap.
- References: shell startup files, scripts in the projects folder, `~/.config/opencode` and LaunchAgents are searched for `OPENCODE_GUARD_BYPASS`, `OPENCODE_SANDBOXED`, `OpenCodeGuard`, `OpenCode Guard` and `opencode-guard`. Each hit is updated or filed.

pi-sandbox-guard:
- Bindings: every line of `~/.config/pi-sandbox-guard/executables.conf` (`pi=`, `omp=`, `node=`) and `.guard-node` still resolves and passes `agent-guard bind --check` and `doctor`.
- Custom wrappers: every wrapper in pi-sandbox-guard's launcher stamp is in `state/wrappers.json` with a matching hash, starts Pi guarded and passes its arguments through.
- Local changes: the legacy bundle's `pi`, `omp`, `pi-sandbox.sb`, `pi-sandbox-preamble.zsh` and extension are compared with pi-sandbox-guard 7ad441f, and with the commit their `.deployed-version` names where it differs. Any difference is a local customization or an older deploy; each is matched by Agent Guard or filed as a gap.
- Pi and OMP settings: Pi's and OMP's settings, `models.json` and extension lists that name pi-sandbox-guard paths still load the guard's extension from its installed folder.
- References: shell startup files, scripts and LaunchAgents are searched for `pi-sandbox-guard`, `PI_SANDBOX`, `npm run deploy`, `npm run bind` and the checkout's path. Each hit is updated or filed.
- Real sessions: Pi and OMP launch, one blocked and one asked command, `/reload`, and an update while a session runs (shared with the 0.2.0 item).

Live under the old name (not leftovers; they stay until step 10d renames or converts them, and the audit only confirms they are current): `~/.local/bin/pi`, `omp`, `pi-sandbox.sb`, `pi-sandbox-preamble.zsh`, the extension folder `~/.pi/agent/extensions/pi-sandbox-guard/`, `~/.config/pi-sandbox-guard/executables.conf`, `.guard-node` and `~/.pi/agent/security-events.log`. Agent Guard's own `state/legacy/replaced/` is uninstall data for entries a fresh install replaced, not a legacy guard file, and stays.

### 2. Gaps

Each gap becomes its own backlog item naming the Mac, the legacy setting and what Agent Guard lacks. A legacy file that a gap depends on is not removed until the gap is fixed in a release or the owner accepts it in writing in that item.

### 3. Cleanup, journaled and repeatable

After the audit passes on a Mac, or its gaps are disposed of:
- OpenCode Guard's forwarders and engine folder: restart the Mac, then run `agent-guard update`. The forwarder removal that already exists (docs/DESIGN.md section 10) removes `$ocg/bin/opencode`, `opencode-gui` and `~/Library/Application Support/OpenCodeGuard`. No waiting period beyond the restart.
- `~/OpenCode Guard` (old list, log and permission backup) and `state/opencode-guard-permissions.json`: removed once the list and permissions lines of the audit pass. This changes the rule that `~/OpenCode Guard` is never removed.
- `state/legacy/pi-sandbox-guard/` (the retired originals, the launcher stamp, the `~/.local/bin/<name>.bak.*` files and `extension-backups/`): removed once the pi-sandbox-guard lines of the audit pass.
- Local checkouts of OpenCode Guard and pi-sandbox-guard on each Mac: removed, or at least never deployed again, because pi-sandbox-guard's deploy scripts overwrite Agent Guard's Pi files.
- Implementation: a cleanup step that agent-guard runs on request (command name decided when built), journaled like the OpenCode Guard retirement, which refuses while the audit has open lines and reports what it removed. Uninstall stops printing steps to reinstate pi-sandbox-guard from the legacy bundle once the bundle is gone; it names the archived repository's final tag instead.
- Code, in the release after every Mac in scope has migrated and restarted: the launcher stops accepting `OPENCODE_SANDBOXED=1`, since no session started under OpenCode Guard can remain. `AGENT_GUARD_SANDBOXED=1` without a snapshot stays until step 9 (docs/DESIGN.md section 7, Nested launch). The migration modules stay while the final releases point users to Agent Guard's installer; removing them is a later, separate decision.
- docs/DESIGN.md: step 11, section 10 rule 10 ("What stays"), section 11 (The adoption, Uninstall, The Pi migration) and the section 12 end states updated to this plan.

### 4. Final releases and archive

- Each project gets a final release, and its `README.md` opens with a notice. Both name Agent Guard, the install command (the `latest/download` one-liner once 0.2.0 is the latest release), what the migration changes and what it keeps, and recovery: the installer rolls back a failed migration; after a successful one, `agent-guard uninstall`, then the project's own install from its final tag.
- The pi-sandbox-guard notes repeat the behavior changes in 0.2.0's release notes for Pi and OMP sessions.
- Open issues and pull requests on both repositories are closed with a pointer to Agent Guard, then each repository is archived.

Out of scope: new Agent Guard features beyond fixes for audit gaps, and any change to OpenCode Guard's or pi-sandbox-guard's behavior.

## Acceptance Criteria

- Every Mac in scope has migrated and has a recorded audit in this item, with each line carried over, live under its old name, a filed gap, or not present.
- Every gap has a backlog item, and each is fixed in a release or accepted in writing before the legacy files it depends on are removed.
- On each migrated Mac after cleanup: `~/Library/Application Support/OpenCodeGuard`, `~/Applications/OpenCode Guard.app`, `~/.config/opencode/plugins/opencode-guard.js`, `~/.cc-safety-net/rules/opencode-guard/`, `~/OpenCode Guard`, `state/opencode-guard-permissions.json` and `state/legacy/pi-sandbox-guard/` do not exist. No `opencode-guard` entry in `rule.json` and no `opencode-guard` PATH block remains. `agent-guard doctor` passes, and OpenCode, Pi and OMP start guarded.
- The cleanup step is journaled: interrupted at each step and rerun, it finishes without error, and it refuses while the audit has open lines.
- After cleanup, uninstall in a disposable home prints recovery steps whose every named file or tag exists.
- The launcher no longer accepts `OPENCODE_SANDBOXED=1`, released in the first release after every Mac in scope has migrated and restarted.
- Both repositories have a final release as their latest, a README notice, no open issues or pull requests, and show as archived on GitHub.
- docs/DESIGN.md describes this plan.

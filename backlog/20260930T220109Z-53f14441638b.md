# Add a staged installer with doctor, update and uninstall

## Description

Replace the copy-in-place installer with a staged installer that installs from a checksummed GitHub release, fails when its self-test fails and leaves the previous version working, and add the `doctor`, `update` and `uninstall` commands. Today `profiles/opencode/install.sh` overwrites files and runs `rm -rf "$engine/vendor"` before validating the replacement, and a failed self-test only adds a warning, so an interrupted or failed update leaves a mixed install (docs/DESIGN.md section 6).

## Scope / Surfaces Affected

- New bootstrap script, published as a release asset. It is the target of the one-line command, for example `/bin/zsh -c "$(curl -fsSL https://github.com/ebrindley/AgentGuard/releases/latest/download/install.sh)"`. The `-c "$(...)"` form keeps the terminal on stdin, so the projects-folder prompt still works; `curl ... | zsh` would not.
- Step 3's `scripts/release.sh`: also builds the release's bootstrap, with the release tag written into it, next to the archive and its checksum file.
- `profiles/opencode/install.sh` and `install.sh` at the repo root: staged install, switch, self-test gate, rollback, version stamp and recovery of an interrupted run.
- `profiles/opencode/uninstall.sh`: runs as `uninstall`, keeps its restore rules, and reports failure through its exit status.
- A command on the shim PATH (proposed `agent-guard`, in `bin/` next to the `opencode` shims) with `doctor`, `update`, `uninstall` and `version`. `doctor` is today's `launch check` under its permanent name; the installer's self-test, `update` and step 6's per-Mac checks run it.
- `engine/launch`, only if the chosen switch mechanism needs it (see Acceptance Criteria, Switch). Generated SBPL does not change.
- Installer tests under `test/`. They run in a disposable home and serve the release from a local folder.
- `README.md`: install, update and uninstall usage, what the checksum proves and how to recover.
- Out of scope: OpenCode Guard detection and migration (step 5), the public GitHub release and repo settings (step 6), package-store protection (step 7), the Rust binary and its admission (step 8), per-launch state files (step 9), Pi (step 10), a DMG, Homebrew, signing and notarization.

## Acceptance Criteria

**Bootstrap and checksum**
- The bootstrap names its own release tag, written into it when the release is built. It downloads that release's archive and checksum file and verifies the SHA-256 before changing any installed file.
- When the download fails or the hash does not match, the bootstrap exits non-zero, names the file and the expected and actual hash, and leaves the installed version, the Guard List, OpenCode config, shell startup files and the app unchanged.
- The archive is downloaded, verified and unpacked inside the write-protected engine folder (`~/Library/Application Support/AgentGuard`), not in `/private/tmp` or `$TMPDIR`, which are writable from inside the guard. A guarded session running during an install cannot change the files between verification and switch.
- When the bootstrap text itself arrives truncated, it runs nothing: all work happens in a function called on the last line.
- The bootstrap passes its arguments (`--projects DIR`) to the release installer.
- `README.md` states that the checksum comes from the same release as the payload, so it detects corruption and mismatched assets, not a compromised publisher, and that the bootstrap is trusted code fetched over HTTPS (docs/DESIGN.md section 6).
- To install a specific release, the user runs that release's bootstrap URL (`releases/download/<tag>/install.sh`). No separate version flag is needed.

**Fresh installs only**
- When an OpenCode Guard install is present (`~/Library/Application Support/OpenCodeGuard` or `~/.config/opencode/plugins/opencode-guard.js`), the installer exits non-zero before any change and says that migration arrives in a later release. Step 5 replaces this refusal with the migration.

**Switch**
- No launch ever runs a mix of two releases. Every shim and launch path on PATH exists at every moment of an install, update or rollback. One way to do this is a folder per release inside the engine folder, with a pointer file replaced by one rename. The launcher still loads profile data only from inside the account-derived engine folder.
- The permission record (`state/permissions.json`) and other state live outside the release folders, so no switch or rollback can drop them.
- The plugin is copied from the staging folder into `~/.config/opencode/plugins` under a temporary name and moved into place with one rename, so an OpenCode that starts during the switch never reads a partial plugin. The temporary name must be one OpenCode does not load; verify this against its plugin loader (docs/DESIGN.md section 10, rule 2).
- Each shell startup file with an Agent Guard PATH block is rewritten in one write: a temporary file next to the resolved target, then a rename. An interrupted rewrite cannot leave a file that had the block without it. Symlinked startup files stay symlinks, and their targets keep their contents and mode.
- The app is built in the staging folder and swapped in by rename. A failed build leaves the previous app in place.
- The rulebook is moved in from the staging folder by rename; today it is copied in place. `rule.json` keeps its temporary-file-and-rename write, and its other entries are preserved.

**Self-test gate**
- The self-test is the staged release's `doctor`, run against the staged version before it replaces the previous one (docs/DESIGN.md section 6). A check that can run only from the fixed engine path or the plugin folder, such as the plugin-load check, runs right after the switch; this step records which checks those are and how the staged copy is tested.
- When a check prints `FAIL`, the installer exits non-zero and prints the failed checks. Before the switch nothing outside the staging folder has changed. After the switch the installer first puts back the previous release, plugin, rulebook, `rule.json`, PATH blocks, app and OpenCode permission values. The previous version then launches from a terminal and from the app. On a fresh install there is no previous version, so a failure after the switch removes what the run added and restores OpenCode permissions; the Guard List stays.
- A skipped check (OpenCode CLI not found, OpenCode.app not found) is reported and does not fail the install.
- The previous release folder is kept until the self-test passes and removed after that.

**Version stamp**
- After the self-test passes, and only then, the installer writes a version stamp in the engine folder: the release version, the source commit and a hash of each installed file (docs/DESIGN.md section 6). A stamp therefore always describes an install that passed its self-test.
- `agent-guard version` prints the stamp and names each installed file whose hash no longer matches it.

**Update**
- `agent-guard update` fetches the latest release's bootstrap and runs it, with the same verification, staging, gate and rollback as a fresh install. When the latest tag equals the stamp, it runs pending maintenance (step 5's forwarder removal), prints that the install is current and changes nothing else. Rerunning the one-liner reinstalls the same release as a repair.
- When `update` or `uninstall` runs inside a guarded session, it exits non-zero before any change and says to run it from a terminal outside the guard. The check is a write probe of the engine state folder: EPERM means guarded, as in the plugin.

**Uninstall**
- `agent-guard uninstall` keeps the current rules. It restores a permission only where the current value still equals the recorded `wrote` value. It removes the PATH blocks, plugin, rulebook entry, app and engine. It keeps `~/Agent Guard`.
- When any restore fails, uninstall saves the permission record to `~/Agent Guard/permissions-backup.json` before removing the engine, names each file it could not restore and exits non-zero. If the record cannot be saved, the engine stays. The current script prints "Agent Guard removed." and exits 0 after a failed restore.
- A rerun after a failed or interrupted uninstall finishes the job with the same result as one complete run.

**Preservation across failed runs and reruns**
- The Guard List is never overwritten. The `--projects` edit keeps its temporary-file-and-rename write.
- For each OpenCode config, the permission record gets its `orig` and the `wrote` value about to be written before the config changes. An interrupted run therefore cannot leave an allow value that uninstall will not restore. Today `wrote` is recorded only after the config write.
- An existing record entry is never replaced: `orig` stays the value from the first install (current `has($f)` rule).
- On a rerun or update, a permission whose current value differs from the recorded `wrote` is a user edit. It is left unchanged and reported. Config keys other than `edit`, `bash` and `external_directory` are never changed.
- When a run is interrupted at any point (signal, full disk, power loss), the next install, update or uninstall first completes the rollback or the switch from what is on disk, then continues. In every intermediate state, `opencode` from a terminal either runs guarded or refuses. It never runs unguarded.

## How to Verify

- Run the installer tests in a disposable home, outside any agent sandbox, with the release served from a local folder. Each case must pass:
  - fresh install through the bootstrap;
  - hash mismatch and truncated download: non-zero exit, no installed file changed;
  - truncated bootstrap text: nothing runs;
  - a release whose self-test fails before the switch, and one whose post-switch check fails, each installed over a working one: non-zero exit, the previous stamp is unchanged and the previous version launches;
  - a forced failure or kill during staging, during the switch and after the switch: the next run recovers, and `opencode` in the disposable home is guarded or refuses at every step;
  - a rerun after the user edits a permission and the Guard List: both edits kept;
  - an interrupted permission write, then uninstall: the original values come back;
  - uninstall with a restore failure: non-zero exit, `permissions-backup.json` present;
  - `update` and `uninstall` inside the guard: refused with no change;
  - an OpenCode Guard fixture present: install refused with no change.
- Rerun `node test/golden.mjs` and the integration checks from step 2. They pass unchanged, which shows the generated SBPL and launch behavior did not change.
- Build a release locally. Its bootstrap names that release's tag, and the archive's hash matches its checksum file.
- In a test install, change one installed file: `agent-guard version` names it.
- Read `README.md` for the one-liner, `update`, `uninstall`, the checksum limit and recovery after a failed install.

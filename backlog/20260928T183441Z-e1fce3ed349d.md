# Check whether agents can modify OpenCode's cached plugins

## Description

## Question

OpenCode installs npm plugins into `~/.cache/opencode`. OpenCode Guard 1.0.3 leaves that folder writable, because it allows all of `~/.cache`. Can an agent inside the guard change cached plugin code that OpenCode loads at the next start? That code could switch off the inner layer, or run unguarded when OpenCode is later started without the guard. This is the same class of problem as Pi's `~/.pi/agent/npm` gap.

## Scope / Surfaces Affected

- Investigation only. No change to OpenCode Guard, which stays at v1.0.3 until the migration.
- The result sets `protected` and `writable` for `profiles/opencode` in docs/DESIGN.md.

## Acceptance Criteria

- Where OpenCode stores and loads plugin code, with evidence (a file and line in OpenCode's source or docs).
- The gap is reproduced or ruled out under the OpenCode Guard 1.0.3 profile.
- A recommendation for the Agent Guard OpenCode profile, stating what breaks if the folder is write-protected.

## How to Verify

- Under `sandbox-exec`, with the profile OpenCode Guard generates, try to change a file in the plugin cache.
- Record the findings in this item.

## Investigation and decision — 2026-09-28

**Finding: reproduced.** OpenCode Guard v1.0.3 permits writes to cached npm
plugin code through its broad `~/.cache` grant. For an already configured npm
plugin, a later process can load the changed entrypoint. The write authority was
measured; subsequent loading is established by source inspection, not by running
a payload. No guard-disabling code, actual user plugin, credentials, or live
configuration was read or modified.

### Version and source evidence

This Mac reports OpenCode **1.18.33** (`/opt/homebrew/Cellar/opencode/1.18.33`).
Its tag resolves to commit `51ef4be1d3c122f18fefb510dca8d778571f4f18`.
`XDG_CACHE_HOME` is unset here, so the default cache root applies.

- [core/global.ts:10–25](https://github.com/anomalyco/opencode/blob/51ef4be1d3c122f18fefb510dca8d778571f4f18/packages/core/src/global.ts#L10)
  derives the OpenCode cache from XDG cache; data, state, logs and the cache's
  `bin` folder have separate purposes.
- [plugin/shared.ts:207–213](https://github.com/anomalyco/opencode/blob/51ef4be1d3c122f18fefb510dca8d778571f4f18/packages/opencode/src/plugin/shared.ts#L207)
  resolves configured npm plugins through `Npm.add`; an unversioned name uses
  `@latest`. This is not automatic execution of arbitrary files in the cache.
- [core/npm.ts:87 and 124–145](https://github.com/anomalyco/opencode/blob/51ef4be1d3c122f18fefb510dca8d778571f4f18/packages/core/src/npm.ts#L87)
  uses `<cache>/packages/<specifier>/node_modules/<package>`. If that package
  directory exists, it resolves the existing entrypoint; otherwise it installs
  into that package store. Its existing-directory path does not restore the
  package bytes before use. The downloaded file's Git blob hash matched GitHub's
  content metadata: `94e573d12da938336fc5922b69fc342e401105e9`.
- [plugin/loader.ts:94–101 and 136–145](https://github.com/anomalyco/opencode/blob/51ef4be1d3c122f18fefb510dca8d778571f4f18/packages/opencode/src/plugin/loader.ts#L136)
  resolves the configured plugin and dynamically imports its selected entrypoint.
- [OpenCode plugin documentation](https://opencode.ai/docs/plugins/#how-plugins-are-installed)
  still describes the older `~/.cache/opencode/node_modules/` layout. That is not
  the only location to protect for the installed version; the probe covers both.
- [OpenCode Guard v1.0.3 profile:6–22](https://github.com/ebrindley/OpenCodeGuard/blob/9242c1ad45c895efd63e903e1b27d7bab53620ad/engine/profile.sb#L6)
  grants writes beneath `~/.cache`; its later protected-path/name rules do not
  cover ordinary cached package entries. Stage 1 deliberately retained this.

### Decision for the future Agent Guard profile

**Recommend write-protecting the npm package store in a separate implementation.**
For the tested version, add the effective OpenCode cache's `packages/` subtree
to `protected`, including its metadata and dependencies. At the default location
this is `~/.cache/opencode/packages`. Keep the existing general cache grant and
place the narrower deny after it. Keep normal data/state, logs, temp, and the
rest of the cache writable. Do not freeze all of `~/.cache` or the whole
OpenCode cache merely to protect plugin packages.

If migration retains an older layout, its `~/.cache/opencode/node_modules` and
associated install metadata must be treated as the same protected package-store
surface. Confirm supported-version paths and any XDG cache relocation when
implementing; a hard-coded default path alone does not cover a relocated store.
No such policy is implemented by this spike or retrofitted into stage 1.

**Compatibility cost:** new/missing plugin packages and dependencies cannot be
installed into a protected store from a guarded process. Package maintenance
must happen in an explicit operator session outside the guard. A fully populated
store has a read/resolve fast path, so existing packages should remain usable;
that is a source-based expectation, not a tested hardened deployment. The loader
can report/skip failed npm plugin installs, so missing plugins cannot be treated
as harmless merely because OpenCode itself starts.

The same store also holds npm language-server packages: for example,
[lsp/server.ts:125](https://github.com/anomalyco/opencode/blob/51ef4be1d3c122f18fefb510dca8d778571f4f18/packages/opencode/src/lsp/server.ts#L125)
uses `Npm.which` for TypeScript, and
[core/npm.ts:200–245](https://github.com/anomalyco/opencode/blob/51ef4be1d3c122f18fefb510dca8d778571f4f18/packages/core/src/npm.ts#L200)
can install a missing binary. Those first-use downloads/repairs also require
operator maintenance. Pre-populated plugin and language-server behavior needs
focused verification in the implementation item.

**Scope and limits:** this is a persistence/in-process plugin-integrity gap,
not a demonstrated Seatbelt escape. A normally guarded restart still runs
modified code under Seatbelt. A later intentionally unguarded start would import
it with that process's ordinary authority. Disabling the inner advisory layer
was not attempted or demonstrated. No claim of full loaded-code integrity or
credential isolation follows from the recommended path deny.

Disposition: investigation complete; protection implementation is **out of scope
— capture proposed**. OpenCodeGuard remains unchanged at v1.0.3. Enforcement
rules and automatic gates added by this spike: **0**.
